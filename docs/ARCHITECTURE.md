# Архитектура ReadyCAD

ReadyCAD — модульный монолит: один исполняемый файл, но код разделён на модули
(статические библиотеки CMake) с **односторонними** зависимостями. Модуль не может
подключить заголовок модуля, от которого он не зависит в CMake: сборка просто не найдёт
этот заголовок. Так граница модулей поддерживается компилятором, а не договорённостью.

## Граф зависимостей

```
                         app (ReadyCAD.exe)
                                │
                               ui ─────────────┐        ImGui, GLFW, nfd (диалоги)
                                │              │
                           production          │        конвейер: изделие → файлы для цеха
                                │              │
                             editor          render     OpenGL (glad)
            ┌──────┬──────┬─────┼──────┐       │
           cam   export   │     │   storage    │        nlohmann/json; export: libHaru (PDF)
            └──┬───┘  │   │     │      │       │
            nesting ◄─┼───┼─────┼──────┘       │        Clipper2 (многоугольники)
               │      │   │     │              │
           detailing ─┼───┘     │         ─────┤
               │     i18n ──────┘              │        тексты: интерфейс и документы
               │      │                        │
             core ◄───┴────────────────────────┘        glm
```

Стрелки упрощены: точные зависимости каждого модуля перечислены в таблице.

| Модуль      | Ответственность | Этап | Зависит от |
|-------------|-----------------|------|------------|
| `core`      | Математика (мм, double), `Aabb`, дерево компонентов мебели (Composite), `Panel`, параметрический пересчёт; кухня: ряды модулей, кушаки, цоколь, столешница с вырезами; вырезы и запилы деталей | 1–3, кухня, формы | glm |
| `i18n`      | Тексты (`TextId` + турецкая таблица), названия вещей модели (видов деталей, кромок, отверстий, фурнитуры), UTF-8, перевод в ASCII, имена файлов | 1, 6, 8, 9 | core |
| `storage`   | Файлы в JSON: проект (`*.rcproj`), профиль цеха (`*.rcprofile`), склад листов (`stock.rcstock`), настройки раскроя и станка ЧПУ; файлы цеха в одной папке | 5, 7, 8, 9 | core, nesting, cam |
| `detailing` | Пильные/чистовые размеры, кромки, присадка «Система 32», крепёж, деталь на плоскости (`FlatPart`, с вырезами), список фурнитуры | 4, 6, кухня | core |
| `nesting`   | Склад листов и остатков (`StockManager`), раскрой на пильном центре (гильотина), нестинг на ЧПУ (No-Fit Polygon), генетический алгоритм, расчёт в фоне | 7 | core, detailing; Clipper2 (скрыто внутри) |
| `export`    | 2D-чертежи (`Drawing`), DXF R12, PDF: спецификации, раскрой, сборочный чертёж, чертежи деталей | 6, 7 | core, detailing, nesting, i18n; libHaru (скрыто внутри) |
| `cam`       | Операции обработки (не зависят от станка), планирование нестинг-центра (инструменты, порядок, маршруты, вырезы изнутри), G-code-постпроцессор с настраиваемым диалектом | 8, кухня | core, detailing, nesting, i18n; Clipper2 (скрыто внутри) |
| `editor`    | Документ, выделение, undo/redo, операции для UI, автоматическая детализация, отказ от правок, после которых изделие нельзя собрать. **Без OpenGL**, поэтому тестируется без окна | 5, 9 | всё выше |
| `production`| Конвейер производства: заказ → детали для раскроя → раскрой → PDF, DXF, программы ЧПУ, CSV → пакет для цеха со сводкой; командная строка без окна | 9 | editor, i18n |
| `render`    | OpenGL 3.3 core: сцена, камера, выбор мышью, RAII-обёртки над объектами GPU; фигурные детали призмами, текстуры декоров | 5, формы, декоры | core, detailing, glad; stb_image (скрыто внутри) |
| `ui`        | Окна ImGui, диалоги, меню экспорта, окна раскроя и склада | 1, 5–9 | editor, production, i18n, render, ImGui |
| `app`       | `main()`: окно или пакетный режим без окна | 1, 9 | ui, production |

Модули GUI (`render`, `ui`, `app`) собираются только при `READYCAD_BUILD_APP=ON`.
Пресет `headless` собирает и тестирует всё остальное без GLFW и OpenGL (подходит для CI).

## Структура директорий

```
ReadyCAD/
├── CMakeLists.txt            корневой: опции, порядок модулей
├── CMakePresets.json         debug / release / headless
├── cmake/                    Dependencies (FetchContent), предупреждения, rc_add_module()
├── third_party/glad/         загрузчик OpenGL 3.3 (сгенерирован один раз и лежит в репозитории)
├── modules/<name>/
│   ├── CMakeLists.txt        rc_add_module(<name> SOURCES ... DEPENDS ... TESTS ...)
│   ├── include/readycad/<name>/   публичный API модуля
│   ├── src/                  реализация (снаружи не видна)
│   └── tests/                юнит-тесты модуля -> bin/readycad_<name>_tests.exe
├── app/                      точка входа; resources/ — иконка программы (вшивается в exe)
├── assets/textures/          картинки декоров (CC0, ambientCG), копируются рядом с exe
├── tests/integration/        межмодульные и сквозные (этап 9) тесты
└── docs/
```

## Соглашения

* **Единицы:** миллиметры везде. **Тип:** `double` (`rc::core::Real`). Перевод во `float`
  делается только в `render` при загрузке данных в видеокарту.
* **Оси:** X — ширина (слева направо), Y — высота (снизу вверх), Z — глубина (от задней стенки
  к фасаду). Начало координат изделия — левый нижний задний угол.
* **Пространства имён:** `rc::<module>` (`rc::core`, `rc::detailing`, ...). Исключение:
  модуль `export` живёт в `rc::exporting`, потому что `export` — ключевое слово C++.
* **Тексты:** только через `rc::i18n::tr(TextId::...)`, и в окнах, и в PDF. Код и комментарии
  пишем на английском, интерфейс и документы на турецком.
* **Ресурсы:** только RAII. `new`/`delete` вручную не пишем; OpenGL-объекты оборачиваются
  в классы с деструктором.
* **Допуск:** `rc::core::kEpsilon = 1e-6` мм. Сравнение длин делается через `nearlyEqual()`,
  оператор `==` для них не используется.

* **Координаты деталей:** `box()` любого компонента задан в координатах **изделия**,
  а не относительно родителя. Пересчёт всё равно идёт от корня целиком, поэтому абсолютные
  координаты проще и ничего не стоят.

## Ядро: дерево компонентов и компоновка (этапы 2–3)

### Дерево (Composite)

```
Product (изделие: габариты + ConstructionRules)
└── Carcass (корпус)
    ├── SideWall ×2, TopPanel, BottomPanel, BackPanel     ← простые детали, по одной Panel
    └── Section (отсек, интерьер корпуса)
        ├── Section, Partition, Section ...                ← деление по X (средники)
        │   └── Section, FixedShelf, Section ...           ← деление по Y (стационарные полки)
        ├── Shelf ...                                      ← полки на полкодержателях
        ├── DrawerStack → Drawer ×N                        ← ящики
        │                 └── DrawerFront, DrawerBoxSide ×2, DrawerBoxEnd ×2, DrawerBottom
        └── Door ×N                                        ← накладные двери отсека
```

* Детей родитель держит в `shared_ptr`. Родителя ребёнок знает по обычному невладеющему
  указателю, поэтому циклов владения нет. Деструктор родителя обнуляет этот указатель
  у детей, которые ещё живы.
* `ComponentId` уникален, имя только для людей. `remove()` и `find()` работают по id.
* Компонент владеет **не более чем одной** `Panel` (`std::optional<Panel>`). У композитов
  панели нет.
* «Корпус с полками», «корпус с фасадами», «корпус с ящиками» — это не отдельные классы,
  а разные **составы** одних и тех же деталей. Их собирает `WardrobeBuilder` (Строитель),
  готовые модели выдаёт `createProduct(CatalogItem)` (Фабрика). Так новая комбинация
  не требует нового класса, а у каждого **вида детали** остаётся свой класс со своими формулами.

### Как родитель учитывает особые правила детей

Принцип: **«ограничения идут вниз, размеры идут вверх, позицию задаёт родитель»**
(так же устроена компоновка во Flutter и Android).

`FurnitureComponent::layout(slot)` — это Template Method из четырёх шагов:

1. `updateSize(slot)` — **собственная формула размера** детали (виртуальная);
2. `updatePosition(slot, size)` — **собственная формула положения** (виртуальная);
3. `updatePanel(slot)` — обновить физическую деталь: материал, чистовые размеры, кромки;
4. `layoutChildren(slot)` — композит выделяет детям слоты и рекурсивно вызывает их `layout()`.

Родитель решает **ГДЕ**: передаёт `LayoutSlot` — область, в которой ребёнок может
находиться, плюс контекст (технологические правила, геометрию корпуса, допустимые наплывы
фасадов). Ребёнок решает **КАК**: по своей формуле вычисляет размер и положение внутри
слота. Например, полка получает от отсека полосу во всю ширину и глубину, а сама вычитает
зазоры по бокам, отступ от фасада и зазор до задней стенки. Задняя стенка получает раму
корпуса и через стратегию крепления (`BackMount`) сама вычисляет, на сколько заходит в паз
с учётом зазора на влажностную деформацию.

Корпус **читает** результаты детей: проём интерьера берётся из готовых боксов боковин,
крышки, дна и задней стенки, а не пересчитывается заново. Поэтому каждая формула
существует в одном месте.

После любого изменения (`setDimensions`, `setFixedSize`, `addShelf`, `setBackMount`...)
вызывается `requestLayout()`, и всё изделие пересчитывается от корня. Результат зависит
только от текущих параметров, а не от истории изменений.

### Принятые конструктивные решения

| Решение | По умолчанию | Где меняется |
|---------|--------------|--------------|
| Крышка | накладная на боковины | `Carcass::setTopJoint` |
| Дно | вкладное, между боковинами | `Carcass::setBottomJoint` |
| Задняя стенка | ХДФ 3 мм в паз (8 мм глубиной, 16 мм от заднего края, зазор 1.5 мм на сторону) | `Carcass::setBackMount`: паз / накладная / вкладная |
| Крепление полки | на полкодержателях: −1 мм с каждой стороны, −20 мм от фасада, −2 мм до задней стенки | `Shelf::setMount`: полкодержатели / евровинты (вплотную к стенкам); отступы в `ConstructionRules` |
| Накладные фасады | 1.5 мм от внешнего края, 3 мм между фасадами | `ConstructionRules` |
| Ящики | шариковые направляющие, 13 мм на сторону, длины 250–650 с шагом 50 | `ConstructionRules` |
| Цоколь | не нужен (решено) | — |

Все числа собраны в `ConstructionRules`. Цех может их настроить, не трогая код.

### Проверка «детали не накладываются»

`findOverlaps(root)` проверяет все пары панелей по `Aabb::intersects`. Касание
пересечением не считается. Законные пересечения (задняя стенка в пазу) деталь объявляет
сама через `allowsOverlapWith()`. Тесты Этапа 3 прогоняют эту проверку после каждого
изменения размеров. С этапа 9 её делает и редактор после каждой правки: правка, которая
добавляет пересечение, отклоняется (см. «Что нашёл случайный пользователь»).

## Деталировка и присадка (этап 4, модуль `detailing`)

### Пильные и чистовые размеры

* **Чистовой** размер — готовая деталь вместе с кромкой. Его хранит `Panel`.
* **Пильный** размер — то, что режет пила: `cutSize(panel, rules)` =
  чистовой − толщина кромки + припуск на фуговку, по каждой кромочной стороне. Результат
  округляется до `rules.cutting.rounding`. Пример: полка 762 × 519, ABS 2 мм на переднем
  торце, фуговка 1 мм → 762 × 518.
* `buildCutList()` собирает спецификацию: одинаковые детали объединяются с количеством,
  флаг текстуры подсказывает раскрою, можно ли поворачивать деталь.
  `edgeBandUsage()` считает расход кромки с запасом на обрезку.

### «Система 32»

Все отверстия корпуса лежат на одной вертикальной сетке с шагом 32 мм. Начало сетки —
средняя плоскость дна (`Carcass::system32OriginY()`).

* Полки на полкодержателях **стоят на отверстии**: пересчёт в ядре ставит их к ближайшему
  отверстию сетки (`rules.system32.snapShelves`). Полки на евровинтах остаются точно там,
  где их поставили.
* Передний ряд отверстий находится в 37 мм от переднего края стенки. Задний ряд отстоит
  от переднего на целое число шагов по 32 мм.
* Ось петли выбирается так, чтобы отверстия планки (ось ± 16 мм) тоже попали на сетку.

### Соединения находятся из геометрии

`findJoints()` перебирает пары деталей и ищет случай «торец одной упирается в пласть
другой»: по одной оси боксы касаются, по двум другим перекрываются площадью. Деталь,
у которой ось толщины совпадает с нормалью контакта, даёт пласть, вторая — торец. Поэтому
списка «что с чем соединяется» в коде нет: крышка с боковинами, дно, средники, стационарные
полки, полки на евровинтах и короба ящиков находятся автоматически, и любая новая
конструкция получит соединения без доработки.

Крепёж выбирается в `rules.joints.fastener`:

| Крепёж | Деталь с пластью | Деталь с торцом |
|--------|------------------|-----------------|
| Конфирмат 7×50 | сквозное Ø7 с **наружной** пласти (там головка) | Ø5, глубина 50 − t + 2 |
| Шкант 8×30 | Ø8 × 12 в пласть контакта | Ø8 × 19 |
| Эксцентрик 15 | Ø5 × 11 под болт | канал Ø8 × 34 и чашка Ø15 × 12.5 на внутренней пласти в 34 мм от торца |

Соединители ставятся в 50 мм от концов соединения и между ними не реже чем через 300 мм.
Шканты-выравниватели (`alignmentDowels`) ставятся в 32 мм от каждого соединителя.

### Конфликты отверстий

* Средник с полками на одной высоте с обеих сторон: глухие отверстия с двух пластей
  укорачиваются так, чтобы между ними оставалось `minWallBetweenHoles` (1 мм). Для 18 мм
  это 8.5 мм вместо 10.
* Если место соединителя уже занято (стационарные полки по обе стороны средника), он
  сдвигается на ±32 мм, а при необходимости дальше, до первого свободного места.
* Одинаковые отверстия (полкодержатель и отверстие планки петли в одной точке)
  объединяются в одно.

### Почему присадка — это производные данные

Отверстия и пазы хранятся в `Panel`, но любой пересчёт ядра их стирает
(`Panel::clearMachining()`). Затем `applyDetailing(product)` строит их заново. Так
устаревшая присадка не может попасть на станок. В этапе 5 редактор будет вызывать
детализацию автоматически после каждого изменения.

### Ручки

Ручки — это **данные производства**, а не код: у каждого цеха свой поставщик. Модель ручки
(`HandleModel`: тип скоба/кнопка, межосевое расстояние, Ø отверстия, габарит, поставщик,
артикул) хранится в каталоге `ConstructionRules::handles.catalog`. Сам `ConstructionRules`
по сути и есть «профиль производства»; в этапе 5 он будет сохраняться в файл.

Фасад (`Door`, `DrawerFront`) хранит не саму ручку, а **ссылку на модель и правило
размещения** (`HandlePlacement`). Отступы считаются от края фасада до ближайшего отверстия.

* **Дверь:** по умолчанию вертикально, по центру высоты, в 40 мм от края, противоположного
  петлям. Если перевесить дверь, ручка сама переходит на другую сторону.
* **Фасад ящика:** по умолчанию горизонтально и по центру.
* Пустой `modelId` означает «ручка по умолчанию для этого цеха». Если поменять её в профиле,
  поменяются все фасады, где ручку не выбирали отдельно.
* `handleGeometry()` в ядре вычисляет положение ручки и её отверстий и проверяет, влезает
  ли она на фасад. Этим пользуются и присадка, и 3D-вид (этап 5).
* Присадка сверлит сквозные отверстия **с лицевой стороны**, чтобы скол при выходе сверла
  был на невидимой стороне. Переключатель `drillOnMachine = false` — «сверлит сборщик на
  объекте»: отверстий в программе нет, но ручки остаются в спецификации фурнитуры.
* Если ручки нет в каталоге или она не влезает на фасад, в отчёте появляется
  предупреждение, а неверные отверстия не создаются.

Пока не сделано (кандидаты на этапы 7–8): отверстия под направляющие ящиков, крепление
фасада ящика.

## Интерфейс и 3D (этап 5)

![ReadyCAD: выбрана дверь](images/stage5-door-selected.png)

### Слои: кто что делает

```
ImGui-окна (ui)  ──вызывают──►  операции (editor/Operations)  ──►  Document::edit()
      ▲                                                               │
      │ читают каждый кадр                                            ▼
Document: product, selection, cutList, detailingReport  ◄── пересчёт ядра + applyDetailing
      │
      ▼
render::buildScene() ──► Renderer (OpenGL, в текстуру) ──► ImGui::Image в окне «3B Görünüm»
```

* **Интерфейс никогда не меняет модель напрямую:** он вызывает именованные операции
  (`setDimensions`, `setShelfCount`, `splitSection`, `setHandle`, ...). Поэтому путь
  «поле ввода → модель → присадка → спецификация» целиком покрыт тестами без окна
  (`modules/editor/tests`). Именно это требовал Этап 5: проверку передачи данных из панели
  параметров в модель.
* **`Document::edit()` реализует три паттерна сразу:**
  * **Memento** — перед изменением сохраняется снимок проекта (JSON), на нём построены
    undo/redo;
  * **строгая гарантия исключений** — если изменение бросает исключение, модель
    восстанавливается из снимка, и в документе не остаётся следов неудачной операции;
  * **слияние шагов** — перетаскивание слайдера генерирует изменение в каждом кадре,
    но все они с одним `mergeKey` дают **один** шаг undo, пока пользователь не отпустит мышь.
* **Выделение хранится как `ComponentId`,** а в снимке undo — как путь в дереве (`TreePath`).
  После undo объекты пересоздаются, но выделение остаётся на том же месте дерева.
* **3D-вид:**
  * сцена (`render::Scene`) строится из модели без OpenGL, поэтому её состав и выбор
    мышью (луч против боксов) тестируются;
  * OpenGL-объекты обёрнуты в RAII (`GlName<Deleter>`), утечки GPU-ресурсов невозможны;
  * картинка рисуется в offscreen-буфер с MSAA 4×, и ImGui показывает её как текстуру
    в докируемом окне.
* **Управление в 3D:** левая кнопка — вращение, правая или средняя — сдвиг, колесо —
  масштаб, щелчок — выбор детали. Выбранная деталь подсвечивается, а дерево
  разворачивается до неё.

| Окно | Содержимое |
|------|------------|

### Файлы

* `*.rcproj` — проект: замысел (габариты, структура, выбор по деталям) и правила цеха, с

  добавления новых настроек.

на английском) — это задача этапа 10.

## Экспорт: DXF и PDF (этап 6, модуль `export`)

![Сборочный чертёж: фасад, фасад без дверей с трассой разреза, разрез A–A](images/stage6-assembly.png)

### Один чертёж, два формата

```
detailing::FlatPart ──► drawPart() ─────────┐
core::Product ───────► drawProductView() ───┼──► Drawing ──► writeDxf()         DXF R12 для CAD/CAM
таблицы, штамп ──────► buildDocumentation() ┘   (слои +     savePdf() (libHaru)  PDF для людей
                       └─ страницы = Drawing     примитивы, мм)
```

* **`Drawing`** — промежуточное 2D-представление, как IR в компиляторе: много «фронтендов»
  (чертёж детали, виды изделия, таблицы) и два «бэкенда» (DXF, PDF). Новый формат
  (SVG, печать) = ещё один бэкенд, а новый вид чертежа сразу доступен во всех форматах.
  * **Слой** задаёт вид линий: имя, цвет ACI для DXF, цвет печати для PDF, тип линии
    (сплошная, штриховая, штрихпунктирная) и толщину пера 0.18 / 0.25 / 0.5 мм (ISO 128).
  * **Примитивы:** отрезок, полилиния (замкнутая, с заливкой), окружность, текст
    (высота заглавных букв, выравнивание, поворот) и размер.
  * **Размер** хранится как размер, а не как набор линий. Каждый бэкенд сам разбирает его
    на выносные линии, стрелки и число (`explode()`); короткие размеры получают стрелки
    снаружи. При вставке на лист в масштабе 1:20 размер запоминает **настоящую** длину.
    Эту ошибку («80» вместо «1600») нашла визуальная проверка, теперь её ловит тест.

### Деталь на плоскости: `FlatPart` (модуль `detailing`)

`PanelFrame` хранит отверстия в локальных осях детали, но эти оси могут быть зеркальным
отражением того, что видит человек. `flatten()` разворачивает деталь так, как её видно
**с выбранной пласти**: u — вправо вдоль длины, v — вверх, начало координат в левом нижнем
углу чистовой детали.

* **Без зеркалирования.** Если локальная тройка осей (длина, ширина, толщина) левая или
  смотрим с нижней пласти, ось v переворачивается. Тест проверяет это для всех деталей
  всех моделей каталога по мировой геометрии.
* **Пласти A и B** (Top и Bottom детали). `ViewFace::Auto` выбирает пласть, где больше
  обработки: у обеих боковин это внутренняя сторона, хотя у левой это Top, а у правой Bottom.
* **Отверстия:** `Near` (в видимой пласти), `Far` (в обратной, чертятся штрихами), `Edge`
  (в торце: точка входа, направление, глубина, высота над пластью).
* **Контур:** какая кромка (U1/U2/G1/G2) с какой стороны чертежа и чем облицована.
* **Заготовка** (пильный размер с припуском на фрезеровку) в тех же координатах.

На этом представлении стоят DXF и PDF. На этапах 7–8 им воспользуются нестинг (контур)
и ЧПУ (обработка с одной стороны).

### DXF

* **Версия R12 (AC1009).** Её читают все: AutoCAD, LibreCAD, QCAD, программы раскроя и ЧПУ.
  В ней не нужны дескрипторы объектов, поэтому файл простой и читаемый.
  Структура: `HEADER → TABLES (LTYPE, LAYER, STYLE) → BLOCKS → ENTITIES → EOF`.
* **Слои — это контракт с CAM-программой:**

| Слой | Что на нём |
|------|------------|
| `CONTOUR` | контур чистовой детали (замкнутая полилиния) |
| `CUT_CONTOUR` | заготовка после пилы |
| `CUTOUT` | вырез насквозь (мойка в столешнице, кабель-канал, вырез внутри любой детали), фрезеруется изнутри |
| `EDGE_BAND` | метки облицованных кромок |
| `DRILL_D5_Z13` | отверстия Ø5 глубиной 13 в видимой пласти (сверлятся сверху) |
| `DRILL_BACK_D7_Z18` | отверстия в обратной пласти (деталь надо перевернуть) |
| `DRILL_EDGE_D8_Z30` | торцевые отверстия: контур отверстия от точки входа |
| `GROOVE_W4_Z8` | паз шириной 4 и глубиной 8 (`GROOVE_BACK_...` с обратной стороны) |
| `TEXT`, `DIMENSIONS` | надписи и размеры (CAM их пропускает) |

  Дробная часть в имени слоя пишется через `p`: `DRILL_D15_Z12p5`.
* **Турецкие буквы:**
  * в тексте пишутся как `\U+XXXX`, это работает при любой кодовой странице;
  * знак диаметра `⌀` превращается в код AutoCAD `%%c`;
  * имена слоёв и файлов переводятся в ASCII (`Çekmece yanı` → `Cekmece_yani`), потому что
    с этим справляются ПО станков и их флешки.
* **Экспорт** (меню «Dışa aktar»):
  * все детали в одном файле, рядами, с подписью «номер, название, количество, размер»;
  * каждая деталь в своём файле в папке `<проект>_DXF`, например `03_Raf_771x558.dxf`.

  Раскладку листов (этап 7) рисуют тот же `drawPart()` и `Drawing::append()` со смещением и поворотом.

### PDF: документация для цеха

| Лист | Содержимое |
|------|------------|
| Genel bilgiler | изделие, габариты, число деталей, расход кромки, потребность в плитах (м²), предупреждения, вид спереди |
| Kesim listesi | деталировка: №, деталь, материал, кол-во, чистовой и пильный размер, кромки U1 U2 G1 G2, текстура. Длинная таблица переносится на следующие листы с повтором шапки |
| Kenar bandı ve bağlantı elemanları | расход кромки и фурнитура: конфирматы, шканты, эксцентрики, полкодержатели, петли, ручки (с артикулом), направляющие ящиков |
| Montaj çizimi | фасад, фасад без дверей, разрез A–A с габаритными и монтажными размерами |
| Parça çizimi | на каждую уникальную деталь: чертёж с кромками, отверстиями и пазами + таблица отверстий (пласть, X, Y, Z, Ø, глубина, тип) |

![Чертёж детали](images/stage6-part.png)

* **Формат листа:**
  * A4–A1, книжная или альбомная ориентация;
  * рамка по ISO 5457 (20 мм слева под подшивку);
  * штамп 180 × 21 мм в правом нижнем углу: изделие, название листа, лист n / N, масштаб,
    дата, фирма, исполнитель.
* **Масштаб** выбирается из стандартного ряда 1:1, 1:2, 1:5, 1:10, 1:15, 1:20, 1:25, 1:50…:
  берётся самый крупный, при котором чертёж вместе с размерами помещается на лист. Виды
  сборочного чертежа идут в один ряд, а если в два ряда масштаб крупнее (A4 книжный), то в два.
* **Виды изделия** строятся в проекционной связи по первому углу (ISO E, как в ГОСТ):
  все виды одного ряда стоят на одной линии пола.
  * Разрез A–A проходит через первый отсек, на 40 % его ширины, чтобы не попасть в щель
    между дверями.
  * Разрезанные детали залиты серым, за плоскостью видно всё до ближайшей стенки.
* **Удаление невидимых линий.** Все детали — прямоугольные параллелепипеды, поэтому точный
  алгоритм получается простым: ребро детали рисуется только там, где его не закрывает деталь,
  целиком лежащая ближе к зрителю. Совпадающие отрезки сливаются.
* **Размеры:**
  * габаритные: ширина, высота, глубина (с фасадами и без);
  * монтажные: ширины отсеков цепочкой над видом, просветы между полками внутри отсеков,
    глубина полки в разрезе;
  * внутренний размер рисуется, только если число помещается между стрелками: при мелком
    масштабе иначе получится каша.
* **libHaru** (C, FetchContent):
  * встраивает TrueType-шрифт подмножеством использованных глифов, понимает UTF-8,
    добавляет таблицу `ToUnicode`, поэтому текст в PDF ищется и копируется;
  * собирается без zlib: страницы не сжаты, тесты читают их содержимое, файл ~0.6–0.8 МБ;
  * заголовки libHaru не выходят за пределы модуля (`PRIVATE`), наружу виден только `Pdf.hpp`.
* **Шрифт:** Noto Sans из `assets/fonts` (этап 10) → Arial / Segoe UI из системы → встроенный
  Helvetica с турецкой кодовой страницей Windows-1254.
  * Таблицы раскладываются по метрикам **того же** шрифта (`PdfFontMetrics`), поэтому
    текст не вылезает из ячеек, а слишком длинный обрезается с «…».
* **Закладки** PDF (оглавление слева) на каждый раздел и каждую деталь.

## Раскрой и нестинг (этап 7, модуль `nesting`)

![Раскрой на пильном центре: сначала деловой остаток со склада, потом целые листы](images/stage7-saw.png)

### Два станка — две задачи

Мебельный цех режет листы на детали двумя видами станков, и у каждого свои правила.

| | Пильный центр («Panel ebatlama») | Нестинг-центр с ЧПУ («CNC nesting») |
|---|---|---|
| Как режет | пила идёт прямо через всю заготовку (гильотинный рез), листы можно резать стопкой | фреза обходит контур каждой детали и прорезает лист насквозь в стол-жертву |
| Детали | только прямоугольники (фигурная деталь — по габариту) | любой контур |
| Между деталями | пропил: ширина пилы, 4.4 мм | диаметр фрезы, 12 мм, плюс дополнительный зазор |
| Края листа | обпил 10 мм с каждой стороны; у делового остатка края уже чистые | поле 10 мм |
| Раскладка | полосы → столбцы → детали в столбце (ступени 1–4) | No-Fit Polygon, деталь кладётся как можно левее, затем ниже |
| Деловой остаток | полоса над последней полосой во всю длину листа, концы полос | полоса справа во всю ширину листа |
| Одинаковые листы | режутся одной стопкой (60 мм / 18 мм = 3 листа) | одна программа на все (этап 8) |

Оба станка используют одно описание задачи, один генетический алгоритм и одну форму
результата. Отличается только **декодер**: он превращает особь алгоритма в раскладку по
правилам своего станка.

### Склад: `StockManager` и `Sheet`

* `Sheet` — запись склада: материал (имя, толщина, текстура), длина × ширина, количество,
  признак делового остатка и примечание («Gardırop · 08.10.2026»). Длина идёт вдоль X, это
  направление текстуры.
* Деталь режется только из листа своего материала: совпадают имя и толщина.
* `offers(material)` возвращает, из чего можно резать, в порядке попыток:
  1. деловые остатки, от самого маленького: они дешевле всего и занимают место на складе;
  2. целые листы со склада;
  3. листы под покупку, без ограничения количества. Их размер берётся из первой записи
     целого листа этого материала. Запись с количеством 0 тоже годится: она задаёт размер
     закупаемого листа. Если записи нет, берётся стандартный лист 2800 × 2100.
* Галочка «Stoktaki artıkları kullan» в окне раскроя (`NestingSettings::useRemnants`, по
  умолчанию включена). Если её снять, `optimize()` убирает деловые остатки из `offers()`:
  заказ режется только из целых листов, сначала со склада, потом под покупку. Так делают,
  когда под проект готовы купить новые листы, а остатки берегут для других заказов. Новые
  обрезки этого заказа всё равно попадают на склад при списании. Выбор хранится в
  `settings.json` рядом со станком, а план помнит его в `NestingResult::settings`: сводка
  `OZET.txt` и страница раскроя в PDF пишут «Stoktaki artıklar kullanılmadı». Ключ
  `--no-remnants` делает то же для одного запуска, файл настроек не меняется.
* Обрезок меньше 300 × 200 мм (`RemnantRules`) считается отходом, больше — деловым остатком.
* `consume(result)` срабатывает после раскроя: списывает использованные листы и добавляет
  новые остатки с примечанием. Операция выполняется целиком или никак. Если склад
  изменился и листов уже не хватает, выдаётся ошибка, а склад остаётся прежним.
* Склад принадлежит мастерской, а не проекту. Он лежит в файле `stock.rcstock`
  в папке пользователя (`%APPDATA%\ReadyCAD`) и общий для всех проектов, поэтому остатки
  одного заказа достаются следующему.
* **Почему JSON, а не база данных.** Записей сотни, пользователь один, файл можно прочитать
  глазами, и новая зависимость не нужна. Запись атомарная: сначала `stock.rcstock.tmp`, потом
  переименование поверх старого файла. Так теперь пишутся все файлы, включая проекты. База
  данных (SQLite или сервер) понадобится, когда склад станут делить несколько рабочих мест.

### Детали для раскроя

* `partsFromCutList()` создаёт одну деталь на строку спецификации, умножая количество на число
  изделий. Контур — пильная заготовка в координатах `FlatPart`: начало в левом нижнем углу
  чистовой детали, деталь лежит пластью с большей обработкой вверх. Нестинг-центр сверлит
  сверху, поэтому на этапе 8 отверстия `FlatPart` перейдут на лист тем же преобразованием, что
  и контур.
* **Повороты** только на 90°, точно, без синусов. Прямоугольнику хватает 0° и 90°: после 180° он
  выглядит так же. Деталь с текстурой можно класть только на 0° или 180°, иначе рисунок пойдёт
  поперёк листа.
* Каждый материал раскраивается отдельно: это независимые задачи.

### Генетический алгоритм (по схеме deepnest)

* **Особь** — порядок, в котором детали кладутся, и поворот каждой детали. **Декодер** кладёт
  детали жадно, по порядку: каждую на первый лист, где она помещается, в лучшее место на нём.
  Если не помещается ни на один открытый лист, открывается следующий по `offers()`.
* **Начальное поколение.** Первая особь кладёт сначала крупные детали, это классическая эвристика.
  Остальные — её мутанты с повышенной частотой мутаций: разброс вокруг хорошего старта лучше
  случайных порядков.
* **Отбор** — турнир из трёх. **Скрещивание** одноточечное с сохранением порядка: начало
  порядка берётся у родителя A, остальные детали идут в порядке родителя B, и каждая деталь
  сохраняет поворот того родителя, от которого пришла. **Мутация** меняет местами соседей
  и поворачивает детали. Лучшие особи (элита) переходят в следующее поколение без изменений.
  Лучшая особь за всё время хранится отдельно, поэтому результат от поколения к поколению не
  ухудшается.
* **Стоимость** раскладки, по порядку важности:
  1. сколько деталей не поместилось;
  2. площадь использованных листов (мм², целое число);
  3. насколько далеко детали заходят в каждый лист.

  Третий критерий оставляет остаток листа одним большим прямоугольником.
* **Параллельность.** Особи одного поколения декодируются на нескольких потоках, повторные
  геномы берутся из памяти. Случайные числа генерирует только главный поток, а декодер —
  чистая функция. Поэтому при одном и том же `seed` результат одинаков на 1 и на 16 потоках,
  и это проверяет тест.
* **Настройки**: размер популяции, число поколений, частота мутаций, элита, `seed`, число
  потоков (0 — все ядра, кроме одного), лимит памяти кэша NFP. Это и есть «нагрузка на железо».

### Пильный центр: гильотинный декодер

Декодер работает в «системе полос»: u вдоль полос, v поперёк. Для полос поперёк листа это
транспонированный лист.

* **Ступень 1** — полосы, высоту полосы задаёт первая деталь в ней. **Ступень 2** — полоса
  режется поперёк на столбцы. **Ступень 3** — столбец режется на уложенные в него детали
  (или деталь отделяется от отхода над ней). **Ступень 4** обрезает деталь, которая уже своего
  столбца.
* `maxStages`:
  * 2 — в полосе только детали её высоты;
  * 3 — в столбце только детали его ширины;
  * 4 — в столбце и более узкие детали.
* Пропил теряется между соседями. Целый лист сначала обпиливается со всех сторон, у остатка
  края уже чистые.
* Если деталь не встаёт в существующие полосы в повороте из генома, пробуется второй поворот,
  если текстура его разрешает.
* **Резы в порядке выполнения**: обпил (0), полосы (1), столбцы (2), прирезки (3, 4). Это
  готовая основа для программы пилы на этапе 8.
* `firstCuts = Auto` раскладывает в обоих направлениях и выбирает лучшее.
* **Стопки.** Одинаковые листы объединяются в одну раскладку с `count`. В одну стопку идёт
  `maxStackHeight / толщина` листов: 60 / 18 → 3.

### Нестинг-центр: No-Fit Polygon

![Нестинг фигурных деталей: L, U, треугольники, шестиугольники в одном листе](images/stage7-shapes.png)

* **NFP(A, B)** — множество положений начала детали B, при которых B пересекает A. Это сумма
  Минковского A ⊕ (−B). На границе NFP детали касаются, снаружи — не пересекаются.
* **IFR** (inner-fit rectangle) — положения, при которых деталь лежит внутри полей листа.
* **Свободная область** = IFR минус объединение NFP уже лежащих деталей (разность Clipper2).
  Каждая её вершина — положение, где деталь касается соседа или края. Из вершин выбирается та,
  где все детали заходят в лист меньше всего, затем самая нижняя, затем самая левая. Детали
  прижимаются влево, справа остаётся сплошной остаток.
* **Зазор под фрезу.** Каждая деталь расширяется на половину зазора, угол достраивается
  «ус» (mitre), поэтому он покрывает скруглённый. Если расширенные детали касаются, исходные
  стоят не ближе зазора.
* **Целые микрометры.** Clipper2 считает в целых числах: 1 единица = 1 мкм. Объединения
  и разности точные. NFP сжимаются на 1 мкм, IFR расширяется на 1 мкм. Без этого Clipper
  выбросил бы свободную область нулевой ширины, и деталь не встала бы в зазор точно по размеру.
* **Быстрый путь.** NFP двух прямоугольников — прямоугольник, для него Clipper не нужен.
  Невыпуклые формы считаются суммой Минковского Clipper2, полости заполняются, как в deepnest:
  место, куда деталь не может попасть, не проходя сквозь соседа, считается занятым.
* **Кэш NFP.** NFP зависит только от двух форм (деталь × поворот), а не от их положения. Он
  считается один раз и используется всеми раскладками всех поколений, его делят все потоки.
  Сверх лимита памяти (по умолчанию 256 МБ) новые NFP не сохраняются: считать дольше, но
  результат тот же.
* **Остаток** — полоса во всю ширину листа справа от деталей, за резом фрезы.

### Результат и где он виден

* `NestingResult`: настройки, с которыми он получен, детали, раскладки листов (одинаковые
  объединены, `count`), детали, которые никуда не помещаются. `usage()` считает по каждому
  материалу листы со склада, из остатков и под покупку, заполнение и новые остатки.
* **Фоновый запуск.** `NestingRun` считает на `std::jthread`, окно не замирает и показывает
  лучшую раскладку живьём. «Durdur» останавливает расчёт на лучшем найденном, деструктор
  тоже останавливает и дожидается потока.
* **Окно «Kesim planı»**:
  * станок, число изделий, «Hesapla» (F5) / «Durdur», «Ayarlar...»;

  * «Stoktan düş...» списывает листы после подтверждения.

### Прочее на этом этапе

* **Clipper2** (Boost License, FetchContent): булевы операции, смещение контуров, суммы
  Минковского. Сам алгоритм раскроя — NFP, декодеры, генетика — написан в модуле. Clipper2
  собирается с `-Werror`, поэтому для него добавлен `-Wno-error`: новое предупреждение
  будущего компилятора не должно ломать сборку.
* `storage` теперь зависит от `nesting` (файл склада) и в `CMakeLists.txt` идёт после него.
  Общие JSON-описания вынесены в `src/Json.hpp`.
* `flatPartOf()` переехал из `export` в `detailing`: он нужен и нестингу.
* `std::shared_mutex` в MinGW (pthread rwlock) примерно в одном запуске из десяти падал, когда
  несколько потоков впервые брали его одновременно. Кэш NFP перешёл на обычный `std::mutex`:
  блокировка держится только на время поиска в таблице.
* Имена тестов только латиницей: `ctest` на Windows передаёт фильтр в Catch2 в другой
  кодировке, и тест с «°» или «—» в имени не находился.
* Новые параметры запуска: `--nesting saw|router`, `--stock`, `--cutting-settings`,
  `--export-pdf`, `--data-dir`. Ими сделаны картинки этого раздела. Скрытый тест `[demo]`
  пишет PDF с нестингом фигурных деталей.

## Программы для ЧПУ (этап 8, модуль `cam`)

![Траектория нестинг-центра: сверление, пазы, контуры, холостые ходы](images/stage8-toolpath.png)

### Три слоя: что, как, на каком языке

```
detailing::FlatPart ──► partMachining() ──► Operation         ЧТО сделать: отверстие, паз, контур
nesting::NestingResult ─► sheetJob() ─────► SheetJob          лист + детали на своих местах
                                               │
                     planSheet(профиль станка) ▼
                                            Program           КАК: инструменты, порядок, глубины, ходы
                                               │
                         Postprocessor::write() ▼
                                       текст программы        на языке конкретного контроллера
```

* **Операции** не зависят от станка:
  * `Drilling` — отверстие в любую из шести граней (`Top`, `Bottom`, `Left`, `Right`, `Front`,
    `Back`): точка входа, Ø, глубина;
  * `Groove` — паз;
  * `Contour` — вырезать деталь по контуру.

  Деталь описывается в координатах `FlatPart`. На листе операции поворачиваются тем же
  преобразованием, что и деталь в раскладке: торцевая грань `Left` после поворота на 90°
  становится `Front`.
* **Планировщик** знает правила одного типа станка. На этом этапе это нестинг-центр, он
  выбирает инструменты, порядок, проходы и холостые ходы. Результат — `Program`: смена
  инструмента, холостой ход, рабочий ход, цикл сверления, комментарий. Координаты в мм от стола
  (z = 0 — низ листа). `analyse()` считает длины ходов, отверстия, смены инструмента и время.
* **Постпроцессор** (`Postprocessor`) переводит `Program` в текст для одного вида контроллеров.

**Как это расширяется:**
* Новый контроллер того же ISO-языка — это новый **диалект**, просто данные, код писать не надо.
* Другой формат файла — ещё один `Postprocessor`.
* Новый тип станка — ещё один планировщик над теми же операциями. Например, станок
  горизонтального сверления возьмёт из `partMachining()` торцевые отверстия и отверстия нижней
  пласти. Поэтому в операциях с самого начала есть все грани, хотя нестинг-центр работает
  только сверху.

### Что нестинг-центр делает с листом

1. **Сверлильная голова.** Отверстия сверху сверлятся сверло за сверлом, диаметр должен
   совпадать с точностью ±0.05 мм. Сквозные идут на 0.3 мм в стол-жертву. Маршрут каждого
   сверла: ближайший сосед, затем 2-opt (переставляет участки маршрута, пока он короче;
   пересечений после этого не остаётся). Сверлится всё, пока лист цельный и жёсткий.
2. **Отверстия без своего сверла** выбирает самая крупная фреза, которая уже отверстия:
   врезание в центре, кольца наружу, проходы по глубине.
3. **Пазы** режет фреза не шире паза. Если паз шире фрезы — несколько параллельных проходов
   змейкой. Глубина набирается проходами.
4. **Контуры** режет контурная фреза:
   * путь центра фрезы — контур, расширенный на радиус; углы достраиваются «усом» (mitre), так что
     углы детали остаются острыми;
   * при попутном фрезеровании контур обходится по часовой стрелке;
   * начало — угол, ближайший к фрезе; глубина набирается проходами;
   * **мелкие детали вырезаются первыми**: освободившись, они хуже всего держатся на вакуумном
     столе. Среди деталей близкого размера выбирается ближайшая.

* **Холостые ходы.** Подъём на безопасную высоту, переезд, опускание на высоту подхода.
  Постпроцессор пишет подъём раньше переезда, а опускание после, поэтому низко над листом
  инструмент не ездит никогда.
* **Защита от ошибок** (`CamError`):
  * контурная фреза шире зазора, который оставил нестинг: она прорезала бы соседние детали;
  * длины фрезы не хватает на толщину листа плюс стол-жертву;
  * таблица инструментов противоречива (`validate()`).
* **Что станок сверху не сделает** (`Leftover`) не теряется, а перечисляется по деталям:
  * отверстия в торцах — их сверлит станок горизонтального сверления;
  * отверстия и пазы нижней пласти — деталь надо перевернуть;
  * операции, для которых нет инструмента.

* **Диалект** (`GCodeDialect`) — то, чем различаются контроллеры, говорящие на ISO G-code:
  * строки начала и конца программы, смена инструмента, включение шпинделя — шаблоны с `{tool}`,
    `{rpm}`, `{name}`, `{thickness}`...;
  * циклы сверления `G81` или явные ходы `G0/G1/G0`;
  * номера строк, вид комментариев, `%`, число знаков;
  * где Z = 0: на столе или на верху листа.
* **Пресеты:**
  * «ISO G-code» — циклы G81, Z0 на столе.
  * «KDT (NcStudio)» — номера строк, `M06`, отверстия явными ходами (годится и для контроллеров
    без циклов). Это **стартовые значения**: номера инструментов и строки начала программы надо
    сверить с настоящим станком.
* Вывод модальный: в строке только изменившиеся оси, подача только когда изменилась. Числа
  пишутся через `std::to_chars`, поэтому точка остаётся точкой при любой локали, а «-0.000» не
  бывает.
* Комментарии только ASCII (`asciiFold`), без скобок внутри: контроллеры часто не понимают
  UTF-8.
* **Коррекцию на радиус фрезы считаем сами**, G41/G42 не используем: путь центра уже в
  программе, она не зависит от того, как контроллер понимает коррекцию.

## Сквозной конвейер (этап 9, модуль `production`)

![Таблица деталей: колонка «Kesim», задняя стенка не идёт в раскрой](images/stage9-cutlist.png)

### Один путь от изделия до файлов

До этапа 9 всё, что связывает модули, жило в `ui`: какие детали отдать в раскрой, проверка, что
раскрой не устарел, имена папок, сбор PDF с раскроем. Тесты этот код не видели, а параметры
командной строки работали только с открытым окном. Теперь это GL-free модуль `production`, и
им пользуются все три входа:

```
                 меню (ui)    командная строка (app)    тесты
                      └──────────────┬──────────────────┘
                                     ▼
Order {Document, количество}  ──►  cuttingParts()   детали для раскроя: строки спецификации × N,
                                     │                без деталей «вне раскроя»
                                     ▼
                                planCutting()       nesting::optimize со складом и настройками
                                     │
                                     ▼
       writeDocumentation / writePartDxfs / writeSheetDxfs / writeCncPrograms / writeCutListCsv
                                     │
                                     ▼
                                writePackage()      всё вместе в одной папке + OZET.txt
```

Поэтому тест проверяет ровно те файлы, которые получает пользователь.

* **`Order`** — документ и сколько изделий сделать. Документ уже держит детализацию и
  спецификацию в актуальном виде (это делает `editor`).
* **`planMatches(order, plan)`** — раскрой ещё относится к изделию в его нынешнем виде (те же
  детали в том же количестве). Каждый писатель файлов отказывается от устаревшего раскроя
  (`ProductionError`). Программа ЧПУ по старому раскрою вырезала бы детали, которых в проекте
  уже нет, а это испорченные листы.
* **`orderName`** — имя файлов: имя файла проекта, иначе имя изделия, иначе «Adsız». В имени
  файла и папки только ASCII (`i18n::safeFileName`): контроллеры станков и флешки не всегда
  понимают турецкие буквы.

### Пакет для цеха

«Dışa aktar → Üretim paketi (hepsi bir klasörde)...» (Ctrl+E) пишет всё в одну новую папку:

```
Musteri_Yilmaz_URETIM/
├── Musteri_Yilmaz.pdf                 документация (с раскроем)
├── Musteri_Yilmaz_kesim_listesi.csv   спецификация для оптимизатора пилы или Excel
├── Musteri_Yilmaz.rcproj              сам проект, по которому сделаны файлы
├── DXF/      деталь — файл
├── KESIM/    лист — файл
├── CNC/      лист — программа (если раскрой для нестинг-центра)
└── OZET.txt  сводка
```

* **Только в пустую или новую папку.** Старая программа для листа, которого в новом раскрое
  нет, не должна оказаться рядом с новыми. Меню само выбирает новое имя: `_URETIM`,
  `_URETIM_2`, ...
* **Всё или ничего.** Сначала планируются все программы ЧПУ: если фреза не подходит к раскрою,
  пакет останавливается до первого файла. При любой ошибке уже записанное удаляется. Удалять
  можно спокойно: папка была пустой, всё в ней записали мы.
* **Если раскрой не рассчитан или устарел**, меню сначала считает его (как F5), а пакет
  записывается, когда расчёт закончится. «Stop» отменяет и пакет.
* **CSV** — мост к пильному центру. Программ для пилы мы не пишем (решено на этапе 8), а
  своя программа-оптимизатор у пилы есть, и она принимает таблицу деталей. Разделитель «;»,
  десятичная запятая, UTF-8 с BOM: так турецкий Excel открывает файл без вопросов.
* **`.rcproj` в пакете** — проект именно в том виде, по которому сделаны файлы. Если потом
  возникнет вопрос «почему деталь такая», ответ лежит рядом.
* **`OZET.txt`** — сводка для человека: колонки выровнены по буквам, а не по байтам («ş» —
  одна буква, но два байта UTF-8), BOM и переводы строк Windows, чтобы и старый Блокнот читал
  её правильно:

```
ReadyCAD — Üretim paketi
========================

Sipariş   :  Çekmeceli gardırop × 2
Tarih     :  12.10.2026
Ölçüler   :  1600 × 2200 × 618 mm
Parçalar  :  84 (82 kesim planında, 2 kesim dışı)

Kesim planı — CNC nesting (freze)
---------------------------------
Malzeme      Toplam levha  Stoktan  Artıktan  Satın alınacak  Doluluk  Yeni artık
Suntalam 18             5        0         0               5      %63           5
...
CNC programları
---------------
CNC/01_Suntalam_18_2800x2100.nc  × 1  5 dk 45 sn  Delik: 42  Takım değişimi: 3
...
Toplam süre: 32 dk 20 sn

CNC'de yapılmayan işlemler
--------------------------
124 kenar deliği (yatay delme makinesinde)
78 alt yüz işlemi (parça çevrilerek)
```

  Время одинаковых листов умножается на их число: стопка из двух одинаковых листов — это
  два прогона одной программы.

### Детали вне раскроя

У каждой панели есть флажок «Kesim planına dahil» (`PanelComponent::inCuttingPlan`, по
умолчанию включён). Выключенная деталь остаётся в спецификации, документах и списке кромки,
но не идёт ни в раскрой, ни в программы ЧПУ. Примеры: задняя стенка или дно ящика из ХДФ,
которые заказывают уже нарезанными; деталь, которую режет другой цех; позже — столешница.

* Флажок есть в свойствах детали и колонкой «Kesim» в таблице деталей: одна галочка меняет
  все детали строки за один шаг отмены (`editor::setInCuttingPlan`).
* Деталь вне раскроя никогда не сливается в одну строку спецификации с такой же деталью в
  раскрое. Номер строки при этом не меняется, поэтому этикетки на раскладке совпадают с PDF.
* В PDF такая строка помечена «*» со сноской, в CSV стоит «Hayır», в `OZET.txt` есть свой
  раздел «Kesim planı dışındaki parçalar».
* Флажок сохраняется в проекте (`"cutting": false`, пишется только у выключенных).

### Командная строка без окна

```
ReadyCAD.exe --open proje.rcproj --count 2 --nesting router --package D:\is\proje
```

Окно не создаётся, OpenGL не нужен. Программа открывает проект (или модель каталога),
считает раскрой со складом и настройками цеха (`--data-dir` или папка пользователя), пишет
пакет, печатает сводку и выходит: код 0 — готово, 1 — ошибка (причина в stderr). Склад только
читается: списать листы — решение человека в окне.

Release-сборка — GUI-программа без своей консоли. Поэтому в пакетном режиме она подключается
к консоли, из которой её запустили (`AttachConsole`), и включает в ней UTF-8. Если вывод
перенаправлен в файл, он туда и идёт. Оболочка оконную программу не ждёт, поэтому в скриптах
вывод направляют в конвейер (`ReadyCAD.exe ... | Out-Host`): тогда PowerShell дожидается
конца и получает код выхода.

### Что нашёл случайный пользователь

Первый длинный прогон дал около двух тысяч пересечений деталей. Это пять видов ошибок, и
все они были в модели, а не в тесте:

| Что | Причина | Исправление |
|-----|---------|-------------|
| Крышка 25 мм на боковинах 18 мм заходит в них на 7 мм | `CarcassFrame` знал одну толщину на весь корпус | в рамке четыре толщины (левая, правая боковина, крышка, дно); каждая формула берёт ту, с которой встречается |
| Торцы ящика заходят в боковину 18 мм, боковины — в дно 6 мм | детали короба брали толщины из `ConstructionRules`, а не настоящие | `Drawer` передаёт своим деталям `DrawerBoxFrame` с их реальными толщинами |
| Двери отсека закрывают фасады ящиков его подотсека | правила «фасады не перекрываются» не было | общая проверка редактора (ниже) |
| Полки на одной высоте или их больше, чем помещается | — | общая проверка редактора |
| Ящики в отсеке ниже нескольких сантиметров получают короб без высоты | — | общая проверка редактора |

**Общая проверка редактора.** `Document::edit` после изменения проверяет, что изделие можно
собрать: ни одна панель не потеряла размер, пар пересекающихся деталей не стало больше. Иначе
изменение отклоняется (`ConstructionError` с турецким текстом «Bu değişiklik yapılamaz:
parçalar çakışır (Kapak — Çekmece kapağı)») и откатывается, как любая неудачная правка.
Правило одно на всё, и новые виды деталей (кухня) получат его бесплатно. Проект из старой
версии с пересечениями откроется: пересечения видны в окне «Uyarılar» (щелчок выделяет
деталь), в начале `OZET.txt` («DİKKAT») и в выводе командной строки.

После исправлений: 3200 случайных правок, 2770 приняты, ни одного пересечения.

Попутно найдено при сохранении: выбор материала и кромки у деталей короба ящика не
сохранялся в проект. Теперь у ящика в файле есть `"box"` (только изменённые детали).

## Кухонный гарнитур (после этапа 9)

Расширение, которого не было в плане из десяти этапов. Решения, принятые вместе:
* ящики такие же, как в шкафах (те же `Drawer` и `DrawerStack`);
* на кухне нужен цоколь;

  пользователь;
* какими будут царги (кушаки), решаю я; моё решение описано ниже;

### Несколько корпусов в одном изделии

До кухни у `Product` был ровно один `Carcass`. Теперь у изделия один ребёнок: `Carcass`
(шкаф, комод, стеллаж) или `Kitchen`:

```
Ürün                        Product
└── Mutfak                  Kitchen: свои размеры, вырезы столешницы
    ├── Alt dolaplar        CabinetRow (Base): модули слева направо
    │   ├── Alt dolap 1     Carcass: кушаки вместо крышки, цоколь, ширина в ряду
    │   │   ├── Yan panel, Ön kuşak, Arka kuşak, Alt tabla, Arkalık, Bölme, Baza
    │   └── ...
    ├── Tezgah              Worktop
    └── Üst dolaplar        CabinetRow (Wall)
        └── Üst dolap 1 ... Carcass
```

Размеры изделия для кухни означают: ширина — длина ряда (стена), высота — верхняя линия
навесных шкафов, глубина — глубина нижних корпусов. Остальное — размеры самой кухни
(`Kitchen::Sizes`): высота корпуса нижнего модуля 720, высота навесного 720, его глубина 320,
глубина столешницы 600. Высота цоколя — правило цеха (`rules.kitchen.plinthHeight = 100`):
она задаётся ножками, которые цех покупает. Отсюда раскладка `Kitchen::layoutChildren`:

```
 ┌─────── навесные шкафы ───────┐  ← верхняя линия = высота изделия
 └──────────────────────────────┘    wallHeight, глубина wallDepth
 ═══════════ столешница ══════════   толщина материала Tezgah 38, глубина worktopDepth
 ┌─────── нижние шкафы ─────────┐
 │                              │    baseHeight (корпус)
 └──────────────────────────────┘
   ▔▔▔▔▔▔▔▔ цоколь ▔▔▔▔▔▔▔▔▔▔▔▔     plinthHeight (правило цеха)
```

Те же правила top-down: кухня даёт ряду полосу, ряд даёт модулю колонку, модуль сам
считает свои детали. Ширины в ряду считаются так же, как ширины колонок отсека: модуль с
фиксированной шириной её сохраняет, автоматические делят остаток поровну. Эта формула
вынесена в общую функцию `distributeSizes()` в `LayoutSlot.hpp`, ею пользуются и `Section`, и
`CabinetRow`. Поэтому при удлинении кухни с 2400 до 2600 растёт только «автоматический»
модуль, а мойка остаётся шириной 600.

Каждый модуль — полноценный `Carcass` со своими фасадами. Фасады отстоят от краёв своего
корпуса на `frontEdgeGap` (1,5 мм), поэтому между фасадами соседних модулей получается
`frontGap` (3 мм) без отдельного правила.

Где код предполагал один корпус и что изменилось:

| Место | Теперь |
|-------|--------|
| Присадка (`applyDetailing`) | корпус за корпусом: соединение, полкодержатель или планка петли никогда не переходят к соседнему модулю. Тест строит случай, где торец крышки одного модуля касается пласти боковины соседнего: геометрически это соединение, но конфирматов там нет |
| Операции редактора с корпусом | по `ComponentId` корпуса (`setTopJoint(doc, carcass, ...)`), а не «корпус изделия» |
| Файл проекта | `"kitchen"` вместо `"carcass"`, формат 2 |
| Интерфейс | свойства выбранного корпуса, а не одного-единственного |

### Новые правила конструкции

| Деталь | Правило | Почему так |
|--------|---------|-----------|
| **Кушаки** (`Rail`, «Ön/Arka kuşak») | вместо крышки две полосы между боковинами, ширина 100 (`rules.kitchen.railWidth`). **Горизонтальные** у обычных нижних модулей; задний лежит на задних кромках, и задняя стенка входит в его паз. **Вертикальные** (на ребре) у мойки и варочной панели; передний у самого фасада, задний — сразу перед задней стенкой, а стенка тогда доходит до верха без паза | столешница лежит на боковинах и крепится снизу через кушаки; крышка под ней не нужна. Под мойкой или варочной панелью горизонтальный кушак оказался бы прямо под чашей или корпусом панели |
| **Цоколь** (`Plinth`, «Baza») | у каждого нижнего модуля свой: полоса высотой 100 под корпусом, отступ 40 от его переднего края (место для носков ног). Коробка корпуса включает зону цоколя, сам корпус начинается выше | длинная полоса на всю кухню не поместится на лист 2800 и всё равно потребует стыков. Стык на границе модуля незаметен, а модель остаётся простой: цоколь зависит только от своего корпуса |
| Нижний модуль | боковины стоят на дне (`bottomJoint = Overlay`) | ножки вкручиваются в дно, нагрузка идёт через него |
| Навесной модуль | крышка между боковинами, боковины на дне | навесы ставятся в верхние углы боковин; снизу виден торец дна, а он обклеен (торцы боковин не видны) |
| Ручки | у нижних дверей вверху, у навесных внизу | там их находит рука |
| **Столешница** (`Worktop`, «Tezgah») | `rules.worktopMaterial` (Tezgah 38), глубина 600, длина — по нижним модулям; кромка спереди и на торцах; **по умолчанию вне раскроя** | обычно её покупают плитой 4100 мм и режут отдельно. Одна галочка «Kesim» включает её в раскрой (ниже — что тогда нужно на складе) |
| **Вырез** (мойка, варочная панель) | свойство нижнего модуля (`Carcass::cutout()`): по центру модуля, передний край выреза в 60 мм от переднего края столешницы. Стандарт: мойка 560 × 480 R15, варочная панель 560 × 490 R5 | так пишут инструкции по установке техники. Вырез принадлежит модулю: двигаешь модуль — двигается и вырез |

Числа для 60-сантиметрового модуля мойки: проём между боковинами 564, вырез 560 —
по 2 мм с каждой стороны; по глубине вырез занимает 60…540, передний вертикальный кушак
стоит на 542…560.

**Вырез должен поместиться.** `Kitchen::misplacedCutouts()` находит вырезы, которые нельзя
сделать:
* до края столешницы или до соседнего выреза остаётся меньше 50 мм (`cutoutMargin`);
* вырез не попадает в проём своего модуля, то есть в плане выходит за боковины, за заднюю
  стенку или на кушак либо крышку под столешницей (чаша мойки или корпус панели упёрлись бы
  в деталь).

Редактор считает такие вырезы так же, как пересечения деталей: правка, после которой их стало
больше, отклоняется с текстом «Bu değişiklik yapılamaz: tezgah kesimi yerine sığmaz
(Alt dolap 2)». Так нельзя поставить мойку 560 в модуль 400, мойку в крайний модуль (до торца
столешницы осталось бы 20 мм) или сменить кушаки мойки на горизонтальные. Правило сразу
поймало ошибку в моей первой версии: варочная панель 490, отцентрированная по глубине
столешницы, задевала передний кушак на 3 мм. Поэтому вырез привязан к переднему краю, как в
инструкциях.

### Вырезы на чертежах и в программах ЧПУ

* **Модель.** `Panel::cutouts()` — отверстия насквозь, прямоугольники со скруглёнными углами в
  координатах детали. Это форма детали, а не присадка: `clearMachining()` их не трогает.
  Столешница получает их от кухни через `LayoutSlot::kitchen` (как `CarcassFrame` у деталей
  корпуса).
* **`FlatPart::cutouts`** — вырезы в той же развёртке, что отверстия (вид сверху, без зеркала).
  `cutoutOutline()` превращает вырез в многоугольник против часовой стрелки, по 8 отрезков на
  скругление (отклонение от дуги 0,1 мм при R15).
* **DXF и PDF.** Слой `CUTOUT` — замкнутый контур выреза (договорённость с CAM: всё на `CUTOUT`
  вырезается насквозь изнутри). Размеры цепочкой под деталью: торец, вырез, перемычка, вырез,
  торец; у каждого выреза — глубина и расстояние от переднего края.

  ![Чертёж столешницы](images/kitchen-worktop.png)
* **Программа нестинг-центра.** `Contour` получил флаг `inner`. Фреза идёт внутри выреза
  (контур сжат на радиус: вырез сохраняет размер). Все вырезы фрезеруются раньше любого
  наружного контура, пока детали ещё держатся в листе. Попутное фрезерование при шпинделе по
  часовой стрелке: снаружи детали — по часовой, внутри выреза — против. Если фреза в вырез
  не помещается, он попадает в «работу для других станков».
* **Раскрой** берёт наружный прямоугольник детали; в вырез другие детали не кладутся.
* **3D.** Столешница рисуется кусками вокруг вырезов (сетка по краям вырезов), скругления в
  3D прямые. Щелчок в вырез попадает в шкаф под ним.

Столешница в раскрое: 2400 мм поместится на стандартный лист 2800 × 2100. Для 3 м нужен склад
с плитами столешницы, например 4100 × 620: при полях фрезы по 10 мм остаётся 600. Так
устроен сквозной тест кухни.

### Попутно: одна строка спецификации — одинаковая обработка

Разбирая кухню, я нашёл ошибку этапов 6–9. Строка спецификации объединяла детали только по
виду, размеру, материалу и кромкам. Но чертёж и программа ЧПУ строятся по первой детали
строки. Правая боковина (её отверстия зеркальны отверстиям левой) получала программу левой, а
в кухне боковины модуля с дверями и модуля с ящиками одного размера стали бы «одной деталью».

Теперь `buildCutList` сравнивает ещё и обработку так, как её показывает чертёж детали
(`FlatPart`: отверстия, пазы, вырезы, без учёта порядка, допуск 0,01 мм), и «руку» зеркальных
деталей: боковины, боковины ящиков, двери (по стороне петель). У такой строки рука в названии:
«Yan panel (sol)», «Kapak (sağ)». У гардероба поэтому боковины и двери теперь в двух строках по
одной детали. Количество деталей прежнее, зато каждая строка описывает одну и ту же деталь.

## Вырезы и запилы деталей (после кухни)

Пожелание научного руководителя: деталь не всегда прямоугольник. Под плинтус нужен запил
боковины, под трубу — вырез в кромке, в столе или ТВ-тумбе — кабель-канал, у полки — скруглённые
углы. Предложение (шесть видов, правила ниже) руководитель принял целиком.

### Шесть видов, привязанных к кромкам

| Вид (в интерфейсе) | Структура | Что задаётся |
|---|---|---|
| Köşe kesimi — запил угла | `CornerNotch` | угол, размер вдоль длины и вдоль ширины детали |
| Köşe yuvarlatma — скругление | `CornerRound` | угол, радиус |
| Köşe pahı — скос | `CornerChamfer` | угол, два катета |
| Kenar kesimi — запил на кромке | `EdgeNotch` | кромка, от какого её угла считать, отступ, длина, глубина |
| İç kesim — вырез внутри | `InnerCutout` | угол, от которого меряется центр, два расстояния, размеры, радиус углов |
| Yuvarlak delik — круглое отверстие | `RoundHole` | так же, диаметр |

Вместе это `std::variant` (`ShapeFeature`, `core/PanelShape.hpp`), список хранится у детали
(`PanelComponent::shape()`) и копируется в `Panel` при раскладке. Углы и кромки называются так
же, как на чертежах: U1, U2 — длинные кромки, G1, G2 — короткие, угол «U1–G1». Положение всегда
отсчитывается от кромок, а не от абсолютных координат: запил под плинтус «U1–G1, 100 × 15»
остаётся в заднем нижнем углу, когда шкаф становится выше, а отверстие, отмеренное от угла
«U2–G2», держится у переднего верхнего угла.

![Боковина с запилом и отверстием](images/shapes-wall.png)

### Контур из кромок

`panelOutline()` обходит деталь против часовой стрелки от угла U1–G1. В каждом углу ставит его
форму (угол, ступеньку запила, дугу, скос), вдоль каждой кромки — её запилы по порядку. Каждая
сторона контура знает, откуда она:

| Сторона | Кромка |
|---|---|
| `Edge` — кусок одной из четырёх кромок | её кромка |
| `Corner` — скругление или скос | кромка длинной стороны угла, если она есть, иначе короткой: клиент ждёт обклеенный край |
| `Notch` — сторона запила | нет: кромкооблицовочный станок не обойдёт внутренний угол |

Тот же обход с параметром `grow` даёт **заготовку**: каждая кромка сдвинута наружу на свой
припуск (фрезеровка минус толщина кромки), а запилы остаются на чистовых местах. Поэтому
чистовой контур, заготовка, её размер и кромки получаются из одной формулы.
Вырезы внутри (`InnerCutout`, `RoundHole`) — те же `PanelCutout`, что у мойки в столешнице, и
проходят тем же путём.

### Можно ли это сделать

Правка формы, как любая другая, отклоняется, если деталь нельзя изготовить:

* **не помещается** (`shapeFits`, «kesim parçaya sığmaz»): две формы в одном углу; запил насквозь
  или до соседнего; контур пересекает сам себя (запилы встретились или наложились); вырез
  выходит за деталь или оставляет меньше `minBridge` = 10 мм материала до края и до соседнего
  выреза;
* **задевает обработку** (`findShapeConflicts`, «delik veya kanal kesime denk gelir»):
  * отверстие в пласти должно лежать в материале всем кругом;
  * отверстие в торце должно входить через уцелевший кусок своей кромки и заканчиваться в материале;
  * паз должен идти по материалу.

Пример на шкафу 560 мм: паз под заднюю стенку идёт на 16…20 мм от задней кромки. Запил под
плинтус 15 мм проходит рядом, а 20 мм перерезал бы паз и отклоняется. Угол, где в торец боковины
входят конфирматы крышки, вырезать нельзя. Проверку делает деталировка (ей нужны отверстия), и
`Document::edit` перед проверкой пересчитывает присадку.

### По всей цепочке

* **Спецификация:** контур входит в сравнение обработки, поэтому скруглённая полка — отдельная
  строка от прямых.
* **Чертежи DXF и PDF:**
  * контур детали (`CONTOUR`) и заготовки (`CUT_CONTOUR`) — настоящей формы;
  * метки кромки идут по обклеенным сторонам, а не через запил;
  * у сторон запила — размеры;
  * на странице детали — строки «Kesimler» с каждой формой («Köşe kesimi U1–G1: 100 × 15»).
* **Раскрой:**
  * фрезерный центр получает заготовку настоящей формы и укладывает её по No-Fit Polygon: на
    этапе 7 мы откладывали фигурные детали модели «на потом», и теперь они есть;
  * пила режет описанный прямоугольник, а в сводке появляется раздел «Testereden sonra yapılacak
    kesimler» — какие детали доделать на ЧПУ или вручную.
* **Программа ЧПУ:**
  * наружный контур идёт по форме, вырезы изнутри, раньше контуров;
  * запил уже фрезы станок вырезать не может: фреза прошла бы над ним. Это определяется так:
    контур, расширенный на радиус фрезы и сжатый обратно, становится полнее. Такой запил
    попадает в «работу для других станков», а не теряется молча.

  ![Траектория фрезы](images/shapes-toolpath.png)
* **3D:** фигурная деталь рисуется призмой. Грань триангулируется методом отсечения «ушей»
  (`render/Triangulate.cpp`): каждое отверстие соединяется с контуром мостиком к видимой
  вершине (метод Эберли), затем по одному отрезаются треугольники-«уши». Стенки идут по
  контуру и вокруг вырезов, рёбра — там, где контур поворачивает. Выбор мышью попадает в
  треугольники (Möller–Trumbore), поэтому щелчок в вырез выбирает то, что за ним. Столешница
  кухни теперь тоже призма, со скруглёнными углами вырезов.
* **Файл проекта:** версия 3, у детали `"shape": [{"type": "cornerNotch", "corner": "L1W1",
  "alongLength": 100, "alongWidth": 15}, ...]`. Файлы версий 1 и 2 открываются.

## Декоры и текстуры (после вырезов)

Второе пожелание научного руководителя: детали в 3D должны выглядеть как настоящий материал.
Пользователь подобрал девять бесшовных текстур с лицензией CC0 (ambientCG):
* четыре дерева;
* три мрамора;
* белый пластик;
* ДСП.

Он повернул их так, чтобы волокна шли слева направо. Они лежат в `assets/textures`, источники и
лицензии — в `assets/textures/SOURCES.txt`.

### Декор — свойство материала

| Что | Где | Зачем |
|-----|-----|-------|
| `Decor`: id, название, картинка (или однотонный цвет), средний цвет, есть ли волокна | `core/Decor.hpp` | данные цеха, как каталог ручек: у каждого цеха декоры своего поставщика |
| `ConstructionRules::decors` — каталог (по умолчанию 11 декоров: 9 картинок, светло-серый, антрацит) | правила изделия | сохраняется вместе с проектом и профилем цеха |
| `Material::decor` — id декора | материал | корпус по умолчанию «Bej ahşap», фасады «Beyaz», столешница «Gri mermer» |

**Другой декор — другой материал.** Раскрой, спецификация и склад различают материалы по имени.
Поэтому `withDecor()` дописывает к имени название декора: «Suntalam 18» → «Suntalam 18 Beyaz»
(название прежнего декора заменяется, а не накапливается). Белые и ореховые детали никогда
не попадут на один лист и в одну строку, а на складе будут отдельными позициями. Имена
материалов по умолчанию остаются прежними («Suntalam 18»), поэтому склад цеха со старыми
названиями по-прежнему подходит.

**Волокна — от декора.** У деревянного декора `grain = true`: материал получает `hasGrain`, и
раскрой не поворачивает детали (правило этапа 7). В 3D рисунок идёт вдоль длины детали —
той оси, которую модель с этапа 2 считает направлением волокон. Однотонный цвет и мрамор
поворачивать можно.

### Как рисуется

* Сцена (`SceneSurface`) несёт для каждой детали её картинку, оси длины и ширины и множитель
  (оранжевый у выделенной). Деталь без декора (задняя стенка, короб ящика) окрашена цветом
  своего вида, как раньше.
* Картинка развёртывается по миллиметрам изделия (одна плитка на 800 мм) прямо во фрагментном
  шейдере, по нормали грани:
  * на пласти — вдоль длины и ширины детали;
  * на длинной кромке — вдоль длины и толщины;
  * на торце — вдоль ширины и толщины.

  Поэтому волокна непрерывно переходят с пласти на кромку, а для каждой детали не нужен свой
  буфер координат.
* `loadImage()` читает JPEG и PNG через `stb_image`. Это один заголовочный файл, подключённый
  через FetchContent и зафиксированный по коммиту; его реализация компилируется в отдельной
  библиотеке без наших флагов предупреждений. Файл читает `std::filesystem`, поэтому турецкие
  имена папок не мешают. Текстура загружается один раз, с мипмапами. Если картинку прочитать
  нельзя, вместо неё рисуется средний цвет декора: программа не падает и не показывает
  белые пятна.
* `assets` копируется рядом с `ReadyCAD.exe` после сборки. Программа ищет эту папку рядом с
  собой, а при запуске из папки сборки — в исходниках (`ui/Assets.cpp`).

## Угловые кухни (после декоров)

Г-образная кухня — ряд шкафов на задней стене и на одной боковой, П-образная — на обеих. Угол
решён так, как принято в мебельных цехах: **слепым угловым шкафом** (kör köşe), нижним и
верхним. Г-образный угловой шкаф со складной дверью — вторая часть этого этапа. Научный
руководитель одобрил план целиком.

![Г-образная кухня](images/corner-kitchen.png)

### Ряд в своих координатах

Главное решение этапа. Каждый ряд (`KitchenRun`) раскладывается в своих координатах, как
прямая кухня: длина по X, фасады к +Z, стена при Z = 0. Кухня ставит его на стену размещением
`Placement`: поворотом вокруг вертикальной оси Y на четверть оборота и сдвигом. Левый ряд
повёрнут на один оборот (смотрит в +X), правый — на три (смотрит в −X).

Почему так:
* формулы шкафов, присадка, спецификация, раскрой, программы ЧПУ и чертежи деталей не знают, у
  какой стены стоит деталь. В модулях `detailing`, `nesting`, `cam` не изменилось ни строчки;
* поворот на кратный 90° угол сохраняет главное свойство модели: всё параллельно осям.
  Габаритная коробка детали остаётся точной коробкой, и проверка пересечений по коробкам
  остаётся точной;
* координаты комнаты нужны только трём потребителям: 3D-сцене, проверке пересечений (детали
  двух стен встречаются в углу) и виду сверху. `FurnitureComponent::placement()` складывает
  размещения предков, `productBox()` даёт коробку в координатах изделия.

Отсюда и сознательное ограничение: диагональные угловые шкафы с фасадом под 45° мы не делаем,
они ломают это свойство.

| Что | Где |
|-----|-----|
| `Placement`: четверти оборота и сдвиг; точка, направление, коробка, ось, вложение | `core/Placement.hpp` |
| `FurnitureComponent::placement()`, `productBox()`, `ownPlacement()` | `core/model/FurnitureComponent.hpp` |
| `KitchenRun`: стена, нижний и верхний ряды, столешница, длина боковой стены; у заднего ряда — углы | `core/model/Kitchen.hpp` |
| `KitchenCorner`: конец заднего ряда, нижний и верхний слепые шкафы | там же |
| `Carcass::setBlindCorner(filler)`, `BlindPanel` (kör panel) | `Carcass.hpp`, `Parts.hpp` |
| `KitchenFrame`: высоты, глубины, `cornerBase` / `cornerWall`; `CornerFrame`; `plinthBeyondStart/End` | `core/model/LayoutSlot.hpp` |
| `makeCorner()`, `KitchenBuilder::sideWall()`, модули с указанием стены | `core/builders/KitchenBuilder.hpp` |

### Угол

```
   задняя стена                       правая стена
  ─────────────────────────────────┐
   …│      угловой шкаф 1100       │
    │  дверь │dolgu│  спрятано 578 │
  ──┴────────┴─────┼───────────────┤
                   │ боковой ряд   │
```

* Угловые шкафы стоят в конце заднего ряда: нижний 1100 мм, верхний 800 мм.
* Боковой ряд начинается там, где кончается спрятанная часть углового шкафа: на глубине шкафов
  заднего ряда плюс фасад (560 + 18 = 578 мм, у верхних 320 + 18 = 338 мм). Обе величины
  считает одна функция кухни (`KitchenFrame::cornerBase`, `cornerWall`). Поэтому угловой шкаф
  и боковой ряд не могут разойтись ни при каком изменении размеров.
* Фасад углового шкафа:
  * дверь на открытой части, петли со стороны, удалённой от угла;
  * глухая панель (kör panel) вровень с дверью — на спрятанной части и на доборной полосе
    50 мм (dolgu). Доборная полоса нужна, чтобы дверь и ручки двух стен не задевали друг друга;
  * дверь кончается за зазор фасадов до панели. Для этого корпус уменьшает напуск фасадов
    своей секции (напуск может стать отрицательным), а полки остаются во всю ширину: в
    слепую часть убирают вещи.
* Цоколь заворачивает за угол. Цоколь углового шкафа доходит до задней грани цоколя боковой
  стены (560 − 40 − 18 = 502 мм от боковой стены). Первый цоколь бокового ряда тянется назад до
  лица цоколя углового шкафа (на 18 + 40 = 58 мм за свой корпус). Без этого во внутреннем углу
  была бы щель.
* Столешница: задняя идёт до боковой стены, боковая начинается от её передней кромки — стык
  встык. На торцах у стены и в стыке кромки нет (`KitchenFrame::startClosed`, `endClosed`).
  Стык под 45° требует особого оборудования и не делается.

### Чертежи

* Вид сверху (`ProductView::Plan`): столешницы со стыком и вырезами под мойку и варочную
  панель, длины стен. Верхних шкафов на нём нет. У угловой кухни этот вид стоит на обложке PDF
  и на отдельной странице «Yerleşim planı».
* Развёртки: «Montaj çizimi — Arka duvar», «— Sağ duvar» и т. д. Это те же три вида, что у
  прямой кухни, для каждого ряда в его координатах: так стену видит монтажник, стоя к ней
  лицом. Виды принимают любое поддерево — изделие целиком или ряд.

![Вид сверху](images/corner-plan.png)

### Файл проекта, формат 5

Задний ряд записан, как прямая кухня раньше, поэтому старые файлы читаются прямыми кухнями.
Боковой ряд лежит под `"left"` / `"right"`: длина, угол (`"corner": {"base", "wall"}`), столешница
и ряды. У углового корпуса есть `"blindFiller"`, у его глухой панели — свои выборы
(`"parts": {"blindPanel": …}`).

### Интерфейс

* «Mutfak»: «Sol duvar» и «Sağ duvar» — галочка и длина стены. Новая стена приходит с углом и
  одним шкафом в каждом ряду. «Duvar» в «Dolap ekle» выбирает, куда добавить шкаф.
* «Köşe»: ширины и доборные полосы нижнего и верхнего шкафа. Угловой шкаф не переставляется,
  не удаляется и не становится автоматическим.
* Дерево: Mutfak → Arka duvar (Alt dolaplar, Tezgah, Üst dolaplar, Sağ köşe → Kör köşe alt
  dolabı, Kör köşe üst dolabı) → Sağ duvar.
* Каталог: «Mutfak (L)» — задняя стена 3000, правая 2400; «Mutfak (U)» — 3200, боковые по 2000.
