# Архитектура ReadyCAD

ReadyCAD — модульный монолит: один исполняемый файл, но код разделён на модули
(статические библиотеки CMake) с **односторонними** зависимостями. Модуль не может
подключить заголовок модуля, от которого он не зависит в CMake: сборка просто не найдёт
этот заголовок. Так граница модулей поддерживается компилятором, а не договорённостью.

## Граф зависимостей

```
                         app (ReadyCAD.exe)
                                │
                               ui ─────────────┐        ImGui, GLFW, nfd (диалоги)
                                │              │
                             editor          render     OpenGL (glad)
            ┌──────┬──────┬─────┼──────┐       │
           cam   export   │     │   storage    │        nlohmann/json; export: libHaru (PDF)
            └──┬───┘  │   │     │      │       │
            nesting   │   │     │      │       │
               │      │   │     │      │       │
           detailing ─┼───┘     │      │  ─────┤
               │     i18n ──────┘      │       │        тексты: интерфейс и документы
               │      │                │       │
             core ◄───┴────────────────┴───────┘        glm
```

Стрелки упрощены: точные зависимости каждого модуля перечислены в таблице.

| Модуль      | Ответственность | Этап | Зависит от |
|-------------|-----------------|------|------------|
| `core`      | Математика (мм, double), `Aabb`, дерево компонентов мебели (Composite), `Panel`, параметрический пересчёт | 1–3 | glm |
| `i18n`      | Тексты (`TextId` + турецкая таблица) и названия вещей модели: видов деталей, кромок, отверстий, фурнитуры | 1, 6 | core |
| `storage`   | Файлы проекта (`*.rcproj`) и профиля цеха (`*.rcprofile`) в JSON | 5 | core |
| `detailing` | Пильные/чистовые размеры, кромки, присадка «Система 32», крепёж, деталь на плоскости (`FlatPart`), список фурнитуры | 4, 6 | core |
| `nesting`   | Склад листов и остатков, раскрой (пильный центр), нестинг (ЧПУ) | 7 | core, detailing |
| `export`    | 2D-чертежи (`Drawing`), DXF R12, PDF: спецификации, сборочный чертёж, чертежи деталей | 6 | core, detailing, nesting, i18n; libHaru (скрыто внутри) |
| `cam`       | Промежуточное описание операций обработки + постпроцессоры | 8 | core, detailing, nesting |
| `editor`    | Документ, выделение, undo/redo, операции для UI, автоматическая детализация. **Без OpenGL**, поэтому тестируется без окна | 5, 9 | всё выше |
| `render`    | OpenGL 3.3 core: сцена, камера, выбор мышью, RAII-обёртки над объектами GPU | 5 | core, detailing, glad |
| `ui`        | Окна ImGui, диалоги, меню экспорта | 1, 5, 6 | editor, i18n, render, ImGui |
| `app`       | `main()` | 1 | ui |

Модули GUI (`render`, `ui`, `app`) собираются только при `READYCAD_BUILD_APP=ON`.
Пресет `headless` собирает и тестирует всё остальное без GLFW и OpenGL (подходит для CI).

## Структура директорий

```
ReadyCAD/
├── CMakeLists.txt            корневой: опции, порядок модулей
├── CMakePresets.json         debug / release / headless
├── cmake/                    Dependencies (FetchContent), предупреждения, rc_add_module()
├── third_party/glad/         загрузчик OpenGL 3.3 (сгенерирован один раз и лежит в репозитории)
├── modules/<name>/
│   ├── CMakeLists.txt        rc_add_module(<name> SOURCES ... DEPENDS ... TESTS ...)
│   ├── include/readycad/<name>/   публичный API модуля
│   ├── src/                  реализация (снаружи не видна)
│   └── tests/                юнит-тесты модуля -> bin/readycad_<name>_tests.exe
├── app/                      точка входа
├── tests/integration/        межмодульные и сквозные (этап 9) тесты
└── docs/
```

## Соглашения

* **Единицы:** миллиметры везде. **Тип:** `double` (`rc::core::Real`). Перевод во `float`
  делается только в `render` при загрузке данных в видеокарту.
* **Оси:** X — ширина (слева направо), Y — высота (снизу вверх), Z — глубина (от задней стенки
  к фасаду). Начало координат изделия — левый нижний задний угол.
* **Пространства имён:** `rc::<module>` (`rc::core`, `rc::detailing`, ...). Исключение:
  модуль `export` живёт в `rc::exporting`, потому что `export` — ключевое слово C++.
* **Тексты:** только через `rc::i18n::tr(TextId::...)`, и в окнах, и в PDF. Код и комментарии
  пишем на английском, интерфейс и документы на турецком.
* **Ресурсы:** только RAII. `new`/`delete` вручную не пишем; OpenGL-объекты оборачиваются
  в классы с деструктором.
* **Допуск:** `rc::core::kEpsilon = 1e-6` мм. Сравнение длин делается через `nearlyEqual()`,
  оператор `==` для них не используется.

* **Координаты деталей:** `box()` любого компонента задан в координатах **изделия**,
  а не относительно родителя. Пересчёт всё равно идёт от корня целиком, поэтому абсолютные
  координаты проще и ничего не стоят.

## Ядро: дерево компонентов и компоновка (этапы 2–3)

### Дерево (Composite)

```
Product (изделие: габариты + ConstructionRules)
└── Carcass (корпус)
    ├── SideWall ×2, TopPanel, BottomPanel, BackPanel     ← простые детали, по одной Panel
    └── Section (отсек, интерьер корпуса)
        ├── Section, Partition, Section ...                ← деление по X (средники)
        │   └── Section, FixedShelf, Section ...           ← деление по Y (стационарные полки)
        ├── Shelf ...                                      ← полки на полкодержателях
        ├── DrawerStack → Drawer ×N                        ← ящики
        │                 └── DrawerFront, DrawerBoxSide ×2, DrawerBoxEnd ×2, DrawerBottom
        └── Door ×N                                        ← накладные двери отсека
```

* Детей родитель держит в `shared_ptr`. Родителя ребёнок знает по обычному невладеющему
  указателю, поэтому циклов владения нет. Деструктор родителя обнуляет этот указатель
  у детей, которые ещё живы.
* `ComponentId` уникален, имя только для людей. `remove()` и `find()` работают по id.
* Компонент владеет **не более чем одной** `Panel` (`std::optional<Panel>`). У композитов
  панели нет.
* «Корпус с полками», «корпус с фасадами», «корпус с ящиками» — это не отдельные классы,
  а разные **составы** одних и тех же деталей. Их собирает `WardrobeBuilder` (Строитель),
  готовые модели выдаёт `createProduct(CatalogItem)` (Фабрика). Так новая комбинация
  не требует нового класса, а у каждого **вида детали** остаётся свой класс со своими формулами.

### Как родитель учитывает особые правила детей

Принцип: **«ограничения идут вниз, размеры идут вверх, позицию задаёт родитель»**
(так же устроена компоновка во Flutter и Android).

`FurnitureComponent::layout(slot)` — это Template Method из четырёх шагов:

1. `updateSize(slot)` — **собственная формула размера** детали (виртуальная);
2. `updatePosition(slot, size)` — **собственная формула положения** (виртуальная);
3. `updatePanel(slot)` — обновить физическую деталь: материал, чистовые размеры, кромки;
4. `layoutChildren(slot)` — композит выделяет детям слоты и рекурсивно вызывает их `layout()`.

Родитель решает **ГДЕ**: передаёт `LayoutSlot` — область, в которой ребёнок может
находиться, плюс контекст (технологические правила, геометрию корпуса, допустимые наплывы
фасадов). Ребёнок решает **КАК**: по своей формуле вычисляет размер и положение внутри
слота. Например, полка получает от отсека полосу во всю ширину и глубину, а сама вычитает
зазоры по бокам, отступ от фасада и зазор до задней стенки. Задняя стенка получает раму
корпуса и через стратегию крепления (`BackMount`) сама вычисляет, на сколько заходит в паз
с учётом зазора на влажностную деформацию.

Корпус **читает** результаты детей: проём интерьера берётся из готовых боксов боковин,
крышки, дна и задней стенки, а не пересчитывается заново. Поэтому каждая формула
существует в одном месте.

После любого изменения (`setDimensions`, `setFixedSize`, `addShelf`, `setBackMount`...)
вызывается `requestLayout()`, и всё изделие пересчитывается от корня. Результат зависит
только от текущих параметров, а не от истории изменений.

### Принятые конструктивные решения

| Решение | По умолчанию | Где меняется |
|---------|--------------|--------------|
| Крышка | накладная на боковины | `Carcass::setTopJoint` |
| Дно | вкладное, между боковинами | `Carcass::setBottomJoint` |
| Задняя стенка | ХДФ 3 мм в паз (8 мм глубиной, 16 мм от заднего края, зазор 1.5 мм на сторону) | `Carcass::setBackMount`: паз / накладная / вкладная |
| Крепление полки | на полкодержателях: −1 мм с каждой стороны, −20 мм от фасада, −2 мм до задней стенки | `Shelf::setMount`: полкодержатели / евровинты (вплотную к стенкам); отступы в `ConstructionRules` |
| Накладные фасады | 1.5 мм от внешнего края, 3 мм между фасадами | `ConstructionRules` |
| Ящики | шариковые направляющие, 13 мм на сторону, длины 250–650 с шагом 50 | `ConstructionRules` |
| Цоколь | не нужен (решено) | — |

Все числа собраны в `ConstructionRules`. Цех может их настроить, не трогая код.

### Проверка «детали не накладываются»

`findOverlaps(root)` проверяет все пары панелей по `Aabb::intersects`. Касание
пересечением не считается. Законные пересечения (задняя стенка в пазу) деталь объявляет
сама через `allowsOverlapWith()`. Тесты Этапа 3 прогоняют эту проверку после каждого
изменения размеров.

## Деталировка и присадка (этап 4, модуль `detailing`)

### Пильные и чистовые размеры

* **Чистовой** размер — готовая деталь вместе с кромкой. Его хранит `Panel`.
* **Пильный** размер — то, что режет пила: `cutSize(panel, rules)` =
  чистовой − толщина кромки + припуск на фуговку, по каждой кромочной стороне. Результат
  округляется до `rules.cutting.rounding`. Пример: полка 762 × 519, ABS 2 мм на переднем
  торце, фуговка 1 мм → 762 × 518.
* `buildCutList()` собирает спецификацию: одинаковые детали объединяются с количеством,
  флаг текстуры подсказывает раскрою, можно ли поворачивать деталь.
  `edgeBandUsage()` считает расход кромки с запасом на обрезку.

### «Система 32»

Все отверстия корпуса лежат на одной вертикальной сетке с шагом 32 мм. Начало сетки —
средняя плоскость дна (`Carcass::system32OriginY()`).

* Полки на полкодержателях **стоят на отверстии**: пересчёт в ядре ставит их к ближайшему
  отверстию сетки (`rules.system32.snapShelves`). Полки на евровинтах остаются точно там,
  где их поставили.
* Передний ряд отверстий находится в 37 мм от переднего края стенки. Задний ряд отстоит
  от переднего на целое число шагов по 32 мм.
* Ось петли выбирается так, чтобы отверстия планки (ось ± 16 мм) тоже попали на сетку.

### Соединения находятся из геометрии

`findJoints()` перебирает пары деталей и ищет случай «торец одной упирается в пласть
другой»: по одной оси боксы касаются, по двум другим перекрываются площадью. Деталь,
у которой ось толщины совпадает с нормалью контакта, даёт пласть, вторая — торец. Поэтому
списка «что с чем соединяется» в коде нет: крышка с боковинами, дно, средники, стационарные
полки, полки на евровинтах и короба ящиков находятся автоматически, и любая новая
конструкция получит соединения без доработки.

Крепёж выбирается в `rules.joints.fastener`:

| Крепёж | Деталь с пластью | Деталь с торцом |
|--------|------------------|-----------------|
| Конфирмат 7×50 | сквозное Ø7 с **наружной** пласти (там головка) | Ø5, глубина 50 − t + 2 |
| Шкант 8×30 | Ø8 × 12 в пласть контакта | Ø8 × 19 |
| Эксцентрик 15 | Ø5 × 11 под болт | канал Ø8 × 34 и чашка Ø15 × 12.5 на внутренней пласти в 34 мм от торца |

Соединители ставятся в 50 мм от концов соединения и между ними не реже чем через 300 мм.
Шканты-выравниватели (`alignmentDowels`) ставятся в 32 мм от каждого соединителя.

### Конфликты отверстий

* Средник с полками на одной высоте с обеих сторон: глухие отверстия с двух пластей
  укорачиваются так, чтобы между ними оставалось `minWallBetweenHoles` (1 мм). Для 18 мм
  это 8.5 мм вместо 10.
* Если место соединителя уже занято (стационарные полки по обе стороны средника), он
  сдвигается на ±32 мм, а при необходимости дальше, до первого свободного места.
* Одинаковые отверстия (полкодержатель и отверстие планки петли в одной точке)
  объединяются в одно.

### Почему присадка — это производные данные

Отверстия и пазы хранятся в `Panel`, но любой пересчёт ядра их стирает
(`Panel::clearMachining()`). Затем `applyDetailing(product)` строит их заново. Так
устаревшая присадка не может попасть на станок. В этапе 5 редактор будет вызывать
детализацию автоматически после каждого изменения.

### Ручки

Ручки — это **данные производства**, а не код: у каждого цеха свой поставщик. Модель ручки
(`HandleModel`: тип скоба/кнопка, межосевое расстояние, Ø отверстия, габарит, поставщик,
артикул) хранится в каталоге `ConstructionRules::handles.catalog`. Сам `ConstructionRules`
по сути и есть «профиль производства»; в этапе 5 он будет сохраняться в файл.

Фасад (`Door`, `DrawerFront`) хранит не саму ручку, а **ссылку на модель и правило
размещения** (`HandlePlacement`). Отступы считаются от края фасада до ближайшего отверстия.

* **Дверь:** по умолчанию вертикально, по центру высоты, в 40 мм от края, противоположного
  петлям. Если перевесить дверь, ручка сама переходит на другую сторону.
* **Фасад ящика:** по умолчанию горизонтально и по центру.
* Пустой `modelId` означает «ручка по умолчанию для этого цеха». Если поменять её в профиле,
  поменяются все фасады, где ручку не выбирали отдельно.
* `handleGeometry()` в ядре вычисляет положение ручки и её отверстий и проверяет, влезает
  ли она на фасад. Этим пользуются и присадка, и 3D-вид (этап 5).
* Присадка сверлит сквозные отверстия **с лицевой стороны**, чтобы скол при выходе сверла
  был на невидимой стороне. Переключатель `drillOnMachine = false` — «сверлит сборщик на
  объекте»: отверстий в программе нет, но ручки остаются в спецификации фурнитуры.
* Если ручки нет в каталоге или она не влезает на фасад, в отчёте появляется
  предупреждение, а неверные отверстия не создаются.

Пока не сделано (кандидаты на этапы 7–8): отверстия под направляющие ящиков, крепление
фасада ящика.

## Интерфейс и 3D (этап 5)

![ReadyCAD: выбрана дверь](images/stage5-door-selected.png)

### Слои: кто что делает

```
ImGui-окна (ui)  ──вызывают──►  операции (editor/Operations)  ──►  Document::edit()
      ▲                                                               │
      │ читают каждый кадр                                            ▼
Document: product, selection, cutList, detailingReport  ◄── пересчёт ядра + applyDetailing
      │
      ▼
render::buildScene() ──► Renderer (OpenGL, в текстуру) ──► ImGui::Image в окне «3B Görünüm»
```

* **Интерфейс никогда не меняет модель напрямую:** он вызывает именованные операции
  (`setDimensions`, `setShelfCount`, `splitSection`, `setHandle`, ...). Поэтому путь
  «поле ввода → модель → присадка → спецификация» целиком покрыт тестами без окна
  (`modules/editor/tests`). Именно это требовал Этап 5: проверку передачи данных из панели
  параметров в модель.
* **`Document::edit()` реализует три паттерна сразу:**
  * **Memento** — перед изменением сохраняется снимок проекта (JSON), на нём построены
    undo/redo;
  * **строгая гарантия исключений** — если изменение бросает исключение, модель
    восстанавливается из снимка, и в документе не остаётся следов неудачной операции;
  * **слияние шагов** — перетаскивание слайдера генерирует изменение в каждом кадре,
    но все они с одним `mergeKey` дают **один** шаг undo, пока пользователь не отпустит мышь.
* **Выделение хранится как `ComponentId`,** а в снимке undo — как путь в дереве (`TreePath`).
  После undo объекты пересоздаются, но выделение остаётся на том же месте дерева.
* **3D-вид:**
  * сцена (`render::Scene`) строится из модели без OpenGL, поэтому её состав и выбор
    мышью (луч против боксов) тестируются;
  * OpenGL-объекты обёрнуты в RAII (`GlName<Deleter>`), утечки GPU-ресурсов невозможны;
  * картинка рисуется в offscreen-буфер с MSAA 4×, и ImGui показывает её как текстуру
    в докируемом окне.
* **Управление в 3D:** левая кнопка — вращение, правая или средняя — сдвиг, колесо —
  масштаб, щелчок — выбор детали. Выбранная деталь подсвечивается, а дерево
  разворачивается до неё.

### Окна

| Окно | Содержимое |
|------|------------|
| Katalog | готовые модели (Фабрика `createProduct`) |
| Parametreler | габариты (слайдеры), конструктив корпуса, профиль цеха (крепёж, сверлить ли ручки) |
| 3B Görünüm | 3D-вид, переключатели «Kapaklar» / «Delikler», «Sığdır» |
| Ürün yapısı | **сверху** дерево изделия, **снизу** свойства выбранного: редактируемые параметры и технические данные (чистовой/пильный размер, кромки, отверстия) |
| Kesim listesi | спецификация с пильными размерами и расход кромки |
| Uyarılar | предупреждения детализации |

### Файлы

* `*.rcproj` — проект: замысел (габариты, структура, выбор по деталям) и правила цеха, с
  которыми он создан. Геометрия и присадка **не сохраняются**: при открытии они
  пересчитываются, поэтому файл не может содержать устаревшую присадку.
* `*.rcprofile` — профиль цеха (`ConstructionRules` + каталог ручек). «Dosya → Atölye profili»
  загружает его в текущий проект; это действие можно отменить.
* Недостающие поля берутся по умолчанию, так что старые файлы открываются и после
  добавления новых настроек.

Пока в интерфейсе нет: перевода предупреждений детализации на турецкий (сейчас они
на английском) — это задача этапа 10.

## Экспорт: DXF и PDF (этап 6, модуль `export`)

![Сборочный чертёж: фасад, фасад без дверей с трассой разреза, разрез A–A](images/stage6-assembly.png)

### Один чертёж, два формата

```
detailing::FlatPart ──► drawPart() ─────────┐
core::Product ───────► drawProductView() ───┼──► Drawing ──► writeDxf()         DXF R12 для CAD/CAM
таблицы, штамп ──────► buildDocumentation() ┘   (слои +     savePdf() (libHaru)  PDF для людей
                       └─ страницы = Drawing     примитивы, мм)
```

* **`Drawing`** — промежуточное 2D-представление, как IR в компиляторе: много «фронтендов»
  (чертёж детали, виды изделия, таблицы) и два «бэкенда» (DXF, PDF). Новый формат
  (SVG, печать) = ещё один бэкенд, а новый вид чертежа сразу доступен во всех форматах.
  * **Слой** задаёт вид линий: имя, цвет ACI для DXF, цвет печати для PDF, тип линии
    (сплошная, штриховая, штрихпунктирная) и толщину пера 0.18 / 0.25 / 0.5 мм (ISO 128).
  * **Примитивы:** отрезок, полилиния (замкнутая, с заливкой), окружность, текст
    (высота заглавных букв, выравнивание, поворот) и размер.
  * **Размер** хранится как размер, а не как набор линий. Каждый бэкенд сам разбирает его
    на выносные линии, стрелки и число (`explode()`); короткие размеры получают стрелки
    снаружи. При вставке на лист в масштабе 1:20 размер запоминает **настоящую** длину.
    Эту ошибку («80» вместо «1600») нашла визуальная проверка, теперь её ловит тест.

### Деталь на плоскости: `FlatPart` (модуль `detailing`)

`PanelFrame` хранит отверстия в локальных осях детали, но эти оси могут быть зеркальным
отражением того, что видит человек. `flatten()` разворачивает деталь так, как её видно
**с выбранной пласти**: u — вправо вдоль длины, v — вверх, начало координат в левом нижнем
углу чистовой детали.

* **Без зеркалирования.** Если локальная тройка осей (длина, ширина, толщина) левая или
  смотрим с нижней пласти, ось v переворачивается. Тест проверяет это для всех деталей
  всех моделей каталога по мировой геометрии.
* **Пласти A и B** (Top и Bottom детали). `ViewFace::Auto` выбирает пласть, где больше
  обработки: у обеих боковин это внутренняя сторона, хотя у левой это Top, а у правой Bottom.
* **Отверстия:** `Near` (в видимой пласти), `Far` (в обратной, чертятся штрихами), `Edge`
  (в торце: точка входа, направление, глубина, высота над пластью).
* **Контур:** какая кромка (U1/U2/G1/G2) с какой стороны чертежа и чем облицована.
* **Заготовка** (пильный размер с припуском на фрезеровку) в тех же координатах.

На этом представлении стоят DXF и PDF. На этапах 7–8 им воспользуются нестинг (контур)
и ЧПУ (обработка с одной стороны).

### DXF

* **Версия R12 (AC1009).** Её читают все: AutoCAD, LibreCAD, QCAD, программы раскроя и ЧПУ.
  В ней не нужны дескрипторы объектов, поэтому файл простой и читаемый.
  Структура: `HEADER → TABLES (LTYPE, LAYER, STYLE) → BLOCKS → ENTITIES → EOF`.
* **Слои — это контракт с CAM-программой:**

| Слой | Что на нём |
|------|------------|
| `CONTOUR` | контур чистовой детали (замкнутая полилиния) |
| `CUT_CONTOUR` | заготовка после пилы |
| `EDGE_BAND` | метки облицованных кромок |
| `DRILL_D5_Z13` | отверстия Ø5 глубиной 13 в видимой пласти (сверлятся сверху) |
| `DRILL_BACK_D7_Z18` | отверстия в обратной пласти (деталь надо перевернуть) |
| `DRILL_EDGE_D8_Z30` | торцевые отверстия: контур отверстия от точки входа |
| `GROOVE_W4_Z8` | паз шириной 4 и глубиной 8 (`GROOVE_BACK_...` с обратной стороны) |
| `TEXT`, `DIMENSIONS` | надписи и размеры (CAM их пропускает) |

  Дробная часть в имени слоя пишется через `p`: `DRILL_D15_Z12p5`.
* **Турецкие буквы:**
  * в тексте пишутся как `\U+XXXX`, это работает при любой кодовой странице;
  * знак диаметра `⌀` превращается в код AutoCAD `%%c`;
  * имена слоёв и файлов переводятся в ASCII (`Çekmece yanı` → `Cekmece_yani`), потому что
    с этим справляются ПО станков и их флешки.
* **Экспорт** (меню «Dışa aktar»):
  * все детали в одном файле, рядами, с подписью «номер, название, количество, размер»;
  * каждая деталь в своём файле в папке `<проект>_DXF`, например `03_Raf_771x558.dxf`.

  Раскладку листов (этап 7) нарисует тот же `drawPart()` + `Drawing::append()` со смещением.

### PDF: документация для цеха

| Лист | Содержимое |
|------|------------|
| Genel bilgiler | изделие, габариты, число деталей, расход кромки, потребность в плитах (м²), предупреждения, вид спереди |
| Kesim listesi | деталировка: №, деталь, материал, кол-во, чистовой и пильный размер, кромки U1 U2 G1 G2, текстура. Длинная таблица переносится на следующие листы с повтором шапки |
| Kenar bandı ve bağlantı elemanları | расход кромки и фурнитура: конфирматы, шканты, эксцентрики, полкодержатели, петли, ручки (с артикулом), направляющие ящиков |
| Montaj çizimi | фасад, фасад без дверей, разрез A–A с габаритными и монтажными размерами |
| Parça çizimi | на каждую уникальную деталь: чертёж с кромками, отверстиями и пазами + таблица отверстий (пласть, X, Y, Z, Ø, глубина, тип) |

![Чертёж детали](images/stage6-part.png)

* **Формат листа:**
  * A4–A1, книжная или альбомная ориентация;
  * рамка по ISO 5457 (20 мм слева под подшивку);
  * штамп 180 × 21 мм в правом нижнем углу: изделие, название листа, лист n / N, масштаб,
    дата, фирма, исполнитель.
* **Масштаб** выбирается из стандартного ряда 1:1, 1:2, 1:5, 1:10, 1:15, 1:20, 1:25, 1:50…:
  берётся самый крупный, при котором чертёж вместе с размерами помещается на лист. Виды
  сборочного чертежа идут в один ряд, а если в два ряда масштаб крупнее (A4 книжный), то в два.
* **Виды изделия** строятся в проекционной связи по первому углу (ISO E, как в ГОСТ):
  все виды одного ряда стоят на одной линии пола.
  * Разрез A–A проходит через первый отсек, на 40 % его ширины, чтобы не попасть в щель
    между дверями.
  * Разрезанные детали залиты серым, за плоскостью видно всё до ближайшей стенки.
* **Удаление невидимых линий.** Все детали — прямоугольные параллелепипеды, поэтому точный
  алгоритм получается простым: ребро детали рисуется только там, где его не закрывает деталь,
  целиком лежащая ближе к зрителю. Совпадающие отрезки сливаются.
* **Размеры:**
  * габаритные: ширина, высота, глубина (с фасадами и без);
  * монтажные: ширины отсеков цепочкой над видом, просветы между полками внутри отсеков,
    глубина полки в разрезе;
  * внутренний размер рисуется, только если число помещается между стрелками: при мелком
    масштабе иначе получится каша.
* **libHaru** (C, FetchContent):
  * встраивает TrueType-шрифт подмножеством использованных глифов, понимает UTF-8,
    добавляет таблицу `ToUnicode`, поэтому текст в PDF ищется и копируется;
  * собирается без zlib: страницы не сжаты, тесты читают их содержимое, файл ~0.6–0.8 МБ;
  * заголовки libHaru не выходят за пределы модуля (`PRIVATE`), наружу виден только `Pdf.hpp`.
* **Шрифт:** Noto Sans из `assets/fonts` (этап 10) → Arial / Segoe UI из системы → встроенный
  Helvetica с турецкой кодовой страницей Windows-1254.
  * Таблицы раскладываются по метрикам **того же** шрифта (`PdfFontMetrics`), поэтому
    текст не вылезает из ячеек, а слишком длинный обрезается с «…».
* **Закладки** PDF (оглавление слева) на каждый раздел и каждую деталь.

### Прочее на этом этапе

* **Модуль `i18n`.** Тексты переехали из `ui`: PDF тоже говорит по-турецки, а `export` не может
  зависеть от `ui` (граф односторонний). Один каталог текстов на всё приложение.
* **Каталоги зависимостей у каждого пресета свои** (`build/<пресет>/_deps`). Раньше общий
  `build/_deps` смешивал объектные файлы зависимостей, собранные с флагами Debug и Release.
* **`tools/render_pdf.ps1`** рендерит страницы PDF в PNG встроенным в Windows движком.
  Так вёрстка проверялась глазами, и так сделаны картинки этого раздела.
