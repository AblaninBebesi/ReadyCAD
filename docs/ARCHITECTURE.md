# Архитектура ReadyCAD

ReadyCAD — модульный монолит: один исполняемый файл, но код разделён на модули
(статические библиотеки CMake) с **односторонними** зависимостями. Модуль не может
подключить заголовок модуля, от которого он не зависит в CMake: сборка просто не найдёт
этот заголовок. Так граница модулей поддерживается компилятором, а не договорённостью.

## Граф зависимостей

```
                         app (ReadyCAD.exe)
                                │
                               ui ─────────────┐        ImGui, GLFW
                                │              │
                             editor          render     OpenGL (glad)
                 ┌──────┬──────┼──────┐         │
                cam   export   │      │         │
                 └──┬───┘      │      │         │
                 nesting ──────┘      │         │
                    │                 │         │
                detailing ────────────┘         │
                    │                           │
                  core  ◄───────────────────────┘        glm
```

| Модуль      | Ответственность | Этап | Зависит от |
|-------------|-----------------|------|------------|
| `core`      | Математика (мм, double), `Aabb`, дерево компонентов мебели (Composite), `Panel`, параметрический пересчёт | 1–3 | glm |
| `detailing` | Пильные/чистовые размеры, кромки, присадка «Система 32», крепёж | 4 | core |
| `nesting`   | Склад листов и остатков, раскрой (пильный центр), нестинг (ЧПУ) | 7 | core, detailing |
| `export`    | DXF, PDF (таблицы деталировки, чертежи) | 6 | core, detailing, nesting |
| `cam`       | Промежуточное описание операций обработки + постпроцессоры | 8 | core, detailing, nesting |
| `editor`    | Документ, выделение, команды undo/redo, каталог, модели представления. **Без OpenGL**, поэтому тестируется без окна | 5, 9 | всё выше |
| `render`    | OpenGL 3.3 core: меши, камера, выбор мышью | 5 | core, glad |
| `ui`        | Окна ImGui, локализация (турецкий) | 1, 5 | editor, render, ImGui |
| `app`       | `main()` | 1 | ui |

Модули GUI (`render`, `ui`, `app`) собираются только при `READYCAD_BUILD_APP=ON`.
Пресет `headless` собирает и тестирует всё остальное без GLFW и OpenGL (подходит для CI).

## Структура директорий

```
ReadyCAD/
├── CMakeLists.txt            корневой: опции, порядок модулей
├── CMakePresets.json         debug / release / headless
├── cmake/                    Dependencies (FetchContent), предупреждения, rc_add_module()
├── third_party/glad/         загрузчик OpenGL 3.3 (сгенерирован один раз и лежит в репозитории)
├── modules/<name>/
│   ├── CMakeLists.txt        rc_add_module(<name> SOURCES ... DEPENDS ... TESTS ...)
│   ├── include/readycad/<name>/   публичный API модуля
│   ├── src/                  реализация (снаружи не видна)
│   └── tests/                юнит-тесты модуля -> bin/readycad_<name>_tests.exe
├── app/                      точка входа
├── tests/integration/        межмодульные и сквозные (этап 9) тесты
└── docs/
```

## Соглашения

* **Единицы:** миллиметры везде. **Тип:** `double` (`rc::core::Real`). Перевод во `float`
  делается только в `render` при загрузке данных в видеокарту.
* **Оси:** X — ширина (слева направо), Y — высота (снизу вверх), Z — глубина (от задней стенки
  к фасаду). Начало координат изделия — левый нижний задний угол.
* **Пространства имён:** `rc::<module>` (`rc::core`, `rc::detailing`, ...).
* **Тексты интерфейса:** только через `rc::ui::tr(TextId::...)`. Код и комментарии пишем
  на английском, интерфейс на турецком.
* **Ресурсы:** только RAII. `new`/`delete` вручную не пишем; OpenGL-объекты оборачиваются
  в классы с деструктором.
* **Допуск:** `rc::core::kEpsilon = 1e-6` мм. Сравнение длин делается через `nearlyEqual()`,
  оператор `==` для них не используется.

## Предложения к эскизу ядра (core_arch_exmpl.txt)

Эскиз хороший, Composite выбран правильно. Перед этапом 2 предлагаю поменять несколько вещей:

1. **Пересчёт «сверху вниз» вместо передачи дельт.** В `propagateResize(delta)` каждый ребёнок
   прибавляет к себе дельту родителя. Такая схема ломается, когда появляются правила:
   полки, распределённые равномерно (дельта высоты делится между промежутками, а не
   прибавляется), минимальные размеры, пропорциональные ящики. Кроме того, ошибки округления
   накапливаются. Предлагаю метод `layout()`: родитель знает **свой** размер и **по правилам**
   вычисляет абсолютный размер и позицию каждого ребёнка (например, «полка = внутренняя ширина
   корпуса, Y = низ + i·шаг»). Результат тогда зависит только от текущих параметров,
   а не от истории изменений.
2. **`Panel` хранит только данные.** Метод `scale()` и `localPosition` лучше держать
   в компоненте, а `Panel` оставить описанием физической детали: материал, толщина, размеры,
   кромки, текстура, присадка. Её заполняет компонент при `layout()`, а читают `detailing`,
   `nesting`, `export` и `cam`.
3. **`double` вместо `float`.** Обоснование есть выше и в `Math.hpp`, тест в `MathTests.cpp`.
4. **Стабильные ID вместо имён.** `remove(name)` удалит все узлы с одинаковым именем
   (например, «Полка»). У каждого компонента будет `ComponentId`, имя остаётся только для
   отображения.
5. **Указатель на родителя.** Нужен для подсветки, кнопки «выделить родителя» и пересчёта
   от изменённого отсека вверх. Детей держим в `shared_ptr` (как в ТЗ), родителя — обычным
   невладеющим указателем, чтобы не было циклов владения и утечек.
6. **`collectParts(std::vector<Part>&)`.** В эскизе `Part` не определён. Предлагаю собирать
   `PanelRef` — ссылку на `Panel` плюс мировую трансформацию. Этого хватит и раскрою, и CAM.
